### pi-session guidance

- **Objective:** nana-objective supplies the nearest project objective unless disabled by user configuration; the shared rules above describe pi-only behavior.
- **Compaction summary:** compaction summaries are pi-owned background state, not the project frontier. Persist carry before a final report or session boundary. Where the HANDOFF points to its issues, the seat posts each unresolved item and open question as one issue, never a HANDOFF line. Otherwise the seat writes each on one HANDOFF line under Next or Open for the owner. Only the seat posts, from the owner's gh account. The seat starts each issue comment it writes with `Seat:`. If posting fails, the report lists the item and the reason. Builders and reviewers put open questions in their report. Issues and the replies on them are public. Label an ask `ask` plus one of `blocking`, `optional` or `parked`, or label a next item `next`. A blocking ask's title ends with "(default: <word>)". First pass each title and body through `node "$HOME/nana-pi/scripts/identity-scan.mjs" --stdin --root "$HOME/nana-pi"`. Post only when the scan exits 0. Then hand-check names, handles, hostnames, work references and project names. The scan knows only four words. Delete a wrong post, never edit it. Before acting on an open ask, read its replies with `gh issue view <number> --comments`.
- **Journal and notify:** journal records session events; notify is a pi extension and may be disabled or silent headlessly.
- **Gate:** Advisory pi gate inspects selected shell commands and protected edit/write targets. It is not a security boundary; see the pack README for exact scope and limits, including the interpreter code-operand path gap for floored settings, auth, MCP and extension files.
- **Post-edit:** configured checks run after successful edits only in pi; absent commands mean no checks. Claude Code has no nana per-edit checks.

### Working pattern

- Builder pushes: builders do not push. They report the branch, the full tip and the seat checks run on it. The seat pushes after verifying, then waits for CI where the project uses it.
- Default worktree root: `~/<repo>-wt/<lane>`; branch: `feat/<lane>`, based on main. One writer per worktree.
- Builder launcher: `pi-worker --lane <name> --brief <file> --out <file>`. Reviewer launcher: `pi-review` for a pi roster entry; `node "$HOME/nana-pi/packages/nana-pack/bin/claude-review.mjs"` for a Claude Code entry.
- Review ladder: Every lane gets one reviewer plus CI. The roster's reviewer reviews every lane. A different model lineage reviews the work. The final review must cover the exact tip that will land, or the accepted tip that `nana-land` merges current main into without conflict (a conflict only in the generated files the land contract names, rebuilt by their own generators, counts as no conflict); every later commit the lane authors needs its own accepted review coverage.
- Plans: a lane is one feature. The seat and one adversarial agent write its must-meet tests, about three to eight, one requirement row each, and the builder builds to them. The seat gives the planner the request and its grounding; an earlier plan is grounding for a decision it records, never a format to copy. Read `$HOME/nana-pi/packages/nana-pack/prompts/planner.md`. Every plan names its threat model: honest variation in our tools' output is in scope, deliberate forgery is out, and a finding outside the model is a residual. Every plan names its precedent, the nearest existing code for each part by path, or none with a reason. Plans get no review round. Urgent fixes ship alone and are hardened in a later lane. Once every reviewer says LAND, nothing more is edited.
- Review bar: `pi-review` appends the review standard to every review it runs; `claude-review` appends the same standard. Their briefs state the threat model but not the bar. A reviewer sends back only for a bug that blocks the feature or a harm the standard lists; every other finding is a known bug, recorded as one line in the known-bug file of the feature it concerns, `docs/known-bugs/<feature>.md` (or the unplaced file in that folder when no feature fits or the project has no tree), and fixed when someone hits it or next works on its feature. A review with no MUST finding says LAND; LAND-WITH-FIXES is retired because `nana-land` accepts only LAND. A confirmation round reviews only the change since the last round, and its brief names that revision.
- Land checklist: resolve review findings or record them as known bugs in their feature's file; use `nana-land` with a clean `main` checkout and clean source, verified review rounds, and CI or the local suite on the reviewed tip; where the project's `AGENTS.md` says CI covers its suite, on the fast-forward path, `nana-land` runs the suite only when the tip's CI cannot stand in; the clean-merge path refuses instead. Revalidate if either checkout changes, and rely on the helper's immediate pre-merge checks, ff-only merge, and containment verification. Where origin is on github.com and the tip tracks a workflow, `nana-land` also refuses until the newest CI run of each workflow for the tip has passed, so push the tip to its open pull request, do not cancel its run, and wait for CI. When main has moved since the accepted tip, `nana-land` merges current main into it; a merge with no conflict lands without new CI or review, and a conflict only in the generated files the land contract names, rebuilt by their own generators, counts as no conflict; every other conflicting merge refuses, so merge main in the lane and get that tip reviewed and through CI. In nana-pi, lanes land without waiting for Windows; Windows runs on main after each land, and a red main blocks further lands. The fix lands through `nana-land` with `--fixes-red <run-id>`. Linux remains advisory. Every commit reaching main must be covered by a revision every reviewer accepted; the one exemption is that conflict-free merge, including generated-file conflicts resolved by their own generators; there are no others, and never commit directly to main. Put HANDOFF and session notes in the reviewed change before its final round; nothing is written after a land. Cleanup is a separate operation, only for a clean `feat/<lane>` worktree contained in `main`. Then run map and README checks and the suite check this project's AGENTS.md names; commit explicit paths and report evidence.
- Default pattern: a change that touches code with tests goes through the pattern; questions and one-line fixes get a direct answer. The builder and reviewer models come from this machine's roster, printed by `node "$HOME/nana-pi/packages/nana-pack/bin/nana-roster.mjs"`. Start a pi reviewer with `pi-review`; start a Claude Code reviewer with `node "$HOME/nana-pi/packages/nana-pack/bin/claude-review.mjs"`. Where pi-worker and pi-review are not on PATH (Windows), run them as `node "$HOME/nana-pi/packages/nana-pack/bin/pi-worker.mjs"` and `node "$HOME/nana-pi/packages/nana-pack/bin/pi-review.mjs"` with the same arguments. Start scout (code scouting and research gathering), planner and adversary through `pi-worker --slot <slot> --brief <file> --out <file>`; a `seat` or `none` role runs in the seat. The seat guide gives Node and PowerShell forms and role scheduling.
- Larger lanes: when the roster sets `largerBuilder`, a seat builds a larger or riskier lane with it through `pi-worker --lane-size larger`, a pi entry or a Claude Code entry alike; a small lane goes through `pi-worker --lane-size small`. A seat that cannot start that builder stops and asks the user rather than starting another. With no `largerBuilder`, the builder builds every lane.
- Seat guide: while a builder or reviewer runs, the seat does not read or judge its partial work, and it acts when the run completes. The full guide is `$HOME/nana-pi/packages/nana-setup/claude/rules/nana-seat.md`; Claude Code loads it as a rule, and pi installs and injects the same guide for seat sessions.
- Project-specific overrides belong in that project's own section AFTER this marker region; `nana-setup project` replaces everything between the markers.
