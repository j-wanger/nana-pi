### pi-session guidance

- **Objective:** nana-objective supplies the nearest project objective unless disabled by user configuration; the shared rules above describe pi-only behavior.
- **Compaction summary:** compaction summaries are pi-owned background state, not the project frontier. Persist unresolved work and the owner's open questions in `HANDOFF.md` before a final report or session boundary.
- **Journal and notify:** journal records session events; notify is a pi extension and may be disabled or silent headlessly.
- **Gate:** Advisory pi gate inspects selected shell commands and protected edit/write targets. It is not a security boundary; see the pack README for exact scope and limits, including the interpreter code-operand path gap for floored settings, auth, MCP and extension files.
- **Post-edit:** configured checks run after successful edits only in pi; absent commands mean no checks. Claude Code has no nana per-edit checks.

### Working pattern

- Default worktree root: `~/<repo>-wt/<lane>`; branch: `feat/<lane>`, based on main. One writer per worktree.
- Review corpus: `docs/reviews/<lane>-<date>/`. Builder launcher: `pi-worker --lane <name> --brief <file> --out <file>`. Reviewer launcher: `pi-review` for a pi roster entry; `node "$HOME/nana-pi/packages/nana-pack/bin/claude-review.mjs"` for a Claude Code entry.
- Review ladder: an ordinary lane gets one final reviewer, the roster's reviewer. An install, hook or gate lane also gets the land reviewer, the seat's wrong-code pairs and one independent check. An install, hook or gate lane changes nana-setup install, uninstall or doctor; a Claude Code hook or a pi extension; the nana-gate policy; or the land and review tools (`nana-land`, `pi-review`, `claude-review`, `review-round`). Every other lane is ordinary. Maximum three rounds per item; a different model lineage reviews the work. The final review must cover the exact tip that will land; every later commit needs its own accepted review coverage.
- Plans: a lane is one feature. The seat and one adversarial agent write its must-meet tests, about three to eight, one requirement row each, and the builder builds to them. Every plan names its threat model: honest variation in our tools' output is in scope, deliberate forgery is out, and a finding outside the model is a residual. Every plan names its precedent, the nearest existing code for each part by path, or none with a reason. Plans get no review round. Urgent fixes ship alone and are hardened in a later lane. Once every reviewer says LAND, nothing more is edited.
- Review bar: `pi-review` appends the review standard to every review it runs; `claude-review` appends the same standard. Their briefs state the threat model and lane class but not the bar. A reviewer sends back only for a bug that blocks the feature or a harm the standard lists; every other finding is a known bug, recorded as one line in the known-bug file of the feature it concerns, `docs/known-bugs/<feature>.md` (or the unplaced file in that folder when no feature fits or the project has no tree), and fixed when someone hits it or next works on its feature. A review with no MUST finding says LAND; LAND-WITH-FIXES is retired because `nana-land` accepts only LAND. A confirmation round reviews only the change since the last round, and its brief names that revision.
- Land checklist: resolve review findings or record them as known bugs in their feature's file; run `review-ledger keep --item <slug> --into <lane-review-folder> --repo <path>` with each fix commit and once before the final round, never during a live review of that worktree; use `nana-land` with a clean `main` checkout and clean source, verified review rounds, and the suite on the reviewed tip; rerun the suite if either checkout changes, and rely on the helper's immediate pre-merge checks, ff-only merge, and containment verification. Where origin is on github.com and the tip tracks a workflow, `nana-land` also refuses until the newest CI run of each workflow for the tip has passed, so push the tip to its open pull request, do not cancel its run, and wait for CI. Every commit reaching main must be covered by a revision every reviewer accepted; there are no exemptions, and never commit directly to main. Put HANDOFF and session notes in the reviewed change before its final round; nothing is written after a land. For a confirmation round over cap, use the standard reason: `confirmation round on the final tip after fixes to named findings or a merge of current main`. Cleanup is a separate operation, only for a clean `feat/<lane>` worktree contained in `main`. Then run map, README, and locked full-suite checks; commit explicit paths and report evidence.
- Default pattern: a change that touches code with tests goes through the pattern; questions and one-line fixes get a direct answer. The builder, reviewer and land models come from this machine's roster, printed by `node "$HOME/nana-pi/packages/nana-pack/bin/nana-roster.mjs"`. Start a pi reviewer with `pi-review`; start a Claude Code reviewer with `node "$HOME/nana-pi/packages/nana-pack/bin/claude-review.mjs"`. Where pi-worker and pi-review are not on PATH (Windows), run them as `node "$HOME/nana-pi/packages/nana-pack/bin/pi-worker.mjs"` and `node "$HOME/nana-pi/packages/nana-pack/bin/pi-review.mjs"` with the same arguments.
- Seat land review: in an install, hook or gate lane, when the roster sets no land model (it prints `land: seat`), the seat writes its land review as `docs/reviews/<lane>-<date>/seat-land.md` in the lane's reviewed change before the final round; the independent slice review still covers every land.
- Larger lanes: when the roster sets `largerBuilder`, a seat builds a larger or riskier lane with it through `pi-worker --lane-size larger`, a pi entry or a Claude Code entry alike; a small lane goes through `pi-worker --lane-size small`. A seat that cannot start that builder stops and asks the user rather than starting another. With no `largerBuilder`, the builder builds every lane.
- Seat guide: while a builder or reviewer runs, the seat does not read or judge its partial work, and it acts when the run completes. The full guide is `$HOME/nana-pi/packages/nana-setup/claude/rules/nana-seat.md`; Claude Code loads it as a rule.
- Project-specific overrides belong in that project's own section AFTER this marker region; `nana-setup project` replaces everything between the markers.
