# FEAT-030 — known bugs

*One line per known bug in this feature, moved from HANDOFF.md on 2026-10-21 and kept word for word. A review finding that does not block a land goes here as one line.*

- Post-edit timeout on Windows (post-edit-win-pin): no test covers a taskkill that starts and then fails, such as on access denied. Its fallback code runs only inside the missing-taskkill check.
- Post-edit timeout on Windows (post-edit-win-pin): with taskkill missing, the pack kills only the shell. The check's own processes keep running, as on macOS and Linux when a kill fails. The fallback check requires them to survive, so whoever makes the fallback end the whole tree must restate that check.
- Post-edit timeout on Windows (post-edit-win-pin): a reused process number, or a dead process its parent has not reaped, reads as alive. Either gives a false failure, never a false pass.
- Post-edit timeout on Windows (post-edit-win-pin, post-edit-win-survivors): a process tree that needs over 2.5 seconds to start fails the timeout and abort kill checks. The Windows leg now blocks release, so a slow runner could stop one. The parallel runner does not run that file alone.
- Post-edit kill tests (post-edit-win-survivors): the timeout check does not first see its checker running. So a missing process number reads as ended. A false pass needs the shell to die before it starts the checker. On Windows the kill lands about 390 ms in. The plan judged that a start guard at 300 ms would flake there.
- Post-edit kill tests (post-edit-win-survivors, win-silent-skips): two older checks still run only on macOS and Linux. They find leftover processes with a tool Windows lacks. One proves a leaked grandchild ends. The other proves a run settles when its kill cannot reach a detached child. Since win-silent-skips, Windows prints a skip line for each. One comment says its checker exits at once, but it keeps running.
- Post-edit kill tests (post-edit-win-survivors): one seat run on a scratch branch is the only proof that broken kill code fails these checks on Windows. No standing check repeats it; CI runs only the working code there.
- Post-edit kill tests (post-edit-win-survivors): an empty process number file also reads as an ended checker in the timeout check. It is a second way past the missing start guard.
- Post-edit kill tests (post-edit-win-survivors): the timeout check's checker-gone line does not require a settled run. The abort check's twin does. Another timeout check still fails a run that hangs.
- Post-edit kill tests (post-edit-win-survivors): the abort check's cleanup aborts the turn a second time. It does no harm.
- Python output in post-edit (win-post-edit-utf8): on Windows with Python before 3.15, a check that opens a file with no named encoding reads it as UTF-8. The owner's terminal reads it in the ANSI code page, so such a check can pass or fail differently under post-edit. The independent check found the same trade on macOS or Linux under a non-UTF-8 locale such as Latin-1. There, a check that read a Latin-1 file now fails loudly. UTF-8 mode also changes how a Python check decodes a non-Python child's output it reads as text. On Windows or under a non-UTF-8 locale, such a check now fails loudly with a decode error where it passed before. The pack README's trade sentence still names only Windows and file opens. The narrower fix, setting only Python's output encoding, breaks a check that prints its Python child's output.
- Python output in post-edit (win-post-edit-utf8): Python before 3.7 ignores the UTF-8 switch. The owner's own setting that turns UTF-8 mode off still decides a check's output. So does the owner's own non-UTF-8 Python output encoding. Either can still show replacement marks.
- Python output in post-edit (win-post-edit-utf8): this lane leaves the model's own bash tool alone. pi itself decodes that tool's output, not post-edit.
- Python output in post-edit (win-post-edit-utf8): the two Python output checks skip on a host whose Python already writes UTF-8 under the forced locale. That covers a host with no Latin-1 locale and Python 3.15 or later. CI's Linux leg skips both. A machine with no Python 3.7 or later on its path fails them, naming the commands tried.
- Python output in post-edit (win-post-edit-utf8): no wrong-code pair runs on Windows. No check pins that pi's own environment stays unchanged after a check; the independent check saw it unchanged.
- Session archive (post-edit-win-survivors, trust-finds-pi): 28 entry headings in the October archive follow text with no blank line between. It is cosmetic; each still shows as a heading.
- Post-edit default time limit (post-edit-timeout-name, plan): the new check reads the setting through a copy of the extension and the pack's library folder. If the extension later imports from outside that folder, the check fails loudly, never falsely.
- Post-edit named values (post-edit-values-named, wrong-code pairs): the message for a check that outlives its kill reads the kill grace by name today. No check reads that message at a retuned grace. A bare number put back there would go stale unnoticed.
- Post-edit named values (post-edit-values-named, independent check): the kill grace check records every timer the test process arms during its run. A future Node or pi that arms its own timer there would turn it red with nothing broken.
- Post-edit output cuts (post-edit-values-named plan): the output cap's cut and the failure output's tail cut can each split a character that takes two units. The model then sees one replacement mark, never a lone half, as the plan records.
- Post-edit named values (post-edit-values-named plan): some tests still assume today's values. The kill tests' 15-second watchdog breaks at a kill grace above about 14.5 seconds. The failure display check breaks at an output cap under about 5 KB.
- Post-edit named values (post-edit-values-named plan): the pack README states the 30-second limit, the 2-second kill grace and the 2000-character tail as plain numbers. No check ties them to the settings, so a retune leaves the README wrong.
