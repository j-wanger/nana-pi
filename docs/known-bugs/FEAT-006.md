*One line per known bug in this feature, moved from HANDOFF.md on 2026-10-21 and kept word for word. A review finding that does not block a land goes here as one line.*

- Roster: for a lane, the Windows evidence is a fake pi package in CI. No real pi has run a lane through the new launch on Windows. Since install-check-review-launch, CI's Windows install check runs a real pi review through both installed pi-review launchers. That review runs offline with a test model; no real model has reviewed there. The launchers refuse pi.dev's managed install, pnpm and Volta 2 with a named reason. On Windows, review-ledger run now starts an npm-installed pi too. Since review-ledger-run-win-launch, it starts an npm-installed claude there as well. The launchers retry a refusal like any failed attempt. A test pins that pi-worker writes the refusal to its output file; none pins pi-review's write. The tests-first reds never ran alone on Windows, because the pull request had merge conflicts. No row pins that a non-lane pi-worker reads no roster. The frozen desk refuses to save a user file holding a roster.
- Seat guide: a rule line cannot prove a seat obeys it; only Jake's Windows seat will show that. An unattended Claude Code session stops background commands after 30 minutes by default, so a seat there would lose a long build. A pi seat waits on its one foreground command. Two plan review notes stay as they are. The runtime table names only the two older Claude rules. The guide's line on the seat's own fixes covers one-line fixes only.
- Roster set: the one-command slot change takes no lock, so a desk save, install or editor write during it is lost. It keeps one backup only, and the next write replaces it. On a machine with no roster, its first change writes the whole default roster. Later default changes then stop reaching that machine until the owner copies the backup back. Its refusal inside a pi model's shell is advisory; a model that clears the variable, and pi older than 0.82.0, pass it. Nobody has checked the pi version on the owner's Windows machine. The change must be the command's first word; after the JSON flag it changes nothing. It checks only the roster, not the gate settings. A hard-linked file loses its other link, and no test pins the kept file mode. On Windows, a program holding the file open can fail the rename; run it again.
- Roster set (review): every change writes an empty larger-builder slot. A second machine whose checkout predates that slot then refuses the roster until it pulls. The README no longer warns of this. Copying the backup back recovers it.
- Roster set (review): the default-roster check types the defaults out by hand instead of reading them by name. Retuning a default then fails that check as well as the one that pins it.
- Roster set (review): no check runs the temp file through a symlinked roster. The README names three refusals, but read and write failures also refuse.
- Lane write guard (win-gate-tmp): on macOS the guard refuses the lane typed through its data-volume firmlink path, as main did.
- Lane write guard (win-gate-tmp): run on its own, the guard's test builds its fixtures in the real home and removes them on exit. One build run left a folder there. Nobody knows why, and the folder is gone now.
- Lane write guard (win-gate-tmp): no test covers long-path prefixes, Git Bash drive paths, driveless paths or the plain real-path fallback. On Linux every spelling check skips in the suite, because the suite's home sits under a temp folder. The gate keeps its own path resolver beside the review tools' one.
- Lane write guard temp folders (lane-guard-temp-root, independent check): a home inside the OS temp folder now turns off temp output there on macOS and Windows. The guard sets that temp folder aside because it holds home. The change fails closed, and /tmp still works on macOS and Linux. Run alone with its home inside the temp folder, the guard's test file turns two older checks red. The suite stays green, because its runner puts home and the temp folder side by side.
- Lane write guard temp folders (lane-guard-temp-root, independent check): the new shared temp-folder module's containment helper takes the outer folder first. The gate's own private helper takes it second. The gate also keeps its own copy of the module's path resolver. Nothing breaks today, but a later caller could pass the folders in the wrong order. The rm-outside-asks module uses the shared helper, and its checks fail if the order flips.
- Lane write guard temp folders (lane-guard-temp-root, plan): a broad temp folder, like a mount point or the lane worktrees' parent, still counts. Only a root or a folder holding home is set aside.
- Lane write guard temp folders (lane-guard-temp-root, plan): on macOS and Linux the guard counts only the temp folder Node picks. It ignores the other two temp settings.
- Lane write guard temp folders (lane-guard-temp-root, plan): a refusal names the lane boundary but not the temp folder the guard set aside.
- Lane write guard temp folders (lane-guard-temp-root, wrong-code pairs): on macOS and Linux no check sets home through a link. So a guard that compares home as typed survives there. The Windows leg catches it through the runner's short name. No check sets a temp folder whose path is a text prefix of home's path but does not hold home. So a text-prefix containment test survives everywhere; it would wrongly refuse, never wrongly allow. No check makes a folder's lookup on disk fail. So the guard's fallback to comparing names goes untested; a guard without it survives.
- Lane write guard temp folders (lane-guard-temp-root, final review): on macOS and Linux /tmp is its own rule and always counts. With home inside /tmp, as on some Linux runners, home stays writable to a lane. Main behaves the same. The pack README now says /tmp counts regardless.
- Lane write guard temp folders (lane-guard-temp-root, final review): on Windows a temp setting of a bare drive letter and colon names that drive's current folder, not its root. So the guard does not set it aside. Nobody sets such a value in practice.
- Lane write guard temp folders (lane-guard-temp-root, both reviews): the guard's test file makes a folder and a link and never removes them. Each run leaves both in the temp folder.
- Lane write guard temp folders (lane-guard-temp-root, final review): on macOS the guard compares folder identity only along home's ordinary path. So the system data volume and the two folders above it still count as temp folders. A temp setting naming the data volume lets a lane write reach home through that spelling. No honest tool sets that.
- Lane write guard temp folders (lane-guard-temp-root, final review): a volume that reports inode zero for every folder would make the guard refuse temp output. That fails closed. Some FAT or network volumes may do this (inferred).
