# FEAT-010 — known bugs

*One line per known bug in this feature, moved from HANDOFF.md on 2026-10-21 and kept word for word. A review finding that does not block a land goes here as one line.*

- rm inside the working folder (gate-rm-workdir): the gate still asks for an absolute target, a dot-named target and a compound command. It asks for every rm from the PowerShell tool. Both err toward asking.
- rm inside the working folder (gate-rm-workdir): the exemption assumes the command runs as typed in the session's working folder. A command prefix in pi's settings that changes folder voids it. So do a shell startup file the environment names and an exported rm function.
- rm inside the working folder (gate-rm-workdir): the git check looks only one level under a target. A target holding a git repository deeper down now runs unasked, where main asked. So does a target holding a policy file deeper down, a mount point or an inner link. Nobody has tested that Git Bash on Windows does not follow an inner junction.
- rm inside the working folder (gate-rm-bare-repo): a bare repository below a target still runs unasked, even one level down. A normal repository one level down asks. The owner's trade on nested repositories stays as it is.
- rm inside the working folder (gate-rm-bare-repo): the gate does not recognise a bare repository whose head file, object folder or ref folder is a link. Older git versions made a linked head file. An rm there still runs unasked.
- rm inside the working folder (gate-rm-bare-repo): the gate asks for an rm in a plain folder inside a bare repository that is not a worktree. It also asks for a path from outside through a bare repository into its worktree. On a disk that ignores letter case, a folder with a lowercase head file and object and ref folders asks too. All three err toward asking.
- rm inside the working folder (gate-rm-bare-repo): every plain rm the exemption checks walks up to the filesystem root. Any .git entry ends the walk, valid or not. git's own search skips an invalid .git entry and keeps walking. So a stray .git file between the working folder and a bare repository above it ends the walk early. An rm there then runs unasked. A planted .git file is forgery, outside the threat model. The walk ignores git's ceiling and boundary settings, so it can only ask more. From 30 folders deep it adds about 1.5 milliseconds to each rm.
- rm outside the working folder (rm-outside-asks, plan): the gate skips a target led by another variable, a command substitution or another user's home. Nor does it judge a relative target after a change of folder it cannot read. Only the variable-led form has a check, because builders' cleanup relies on it.
- rm outside the working folder (rm-outside-asks, plan): a session started in home or at a filesystem root sees nothing under it as outside.
- rm outside the working folder (rm-outside-asks, plan): every session shares the temp folders. So a plain rm of another session's file there runs unasked, such as a reviewer's checkout in the temp folder. On macOS and Linux /tmp counts even with home inside it. A plain rm in such a home then runs unasked, as on main. The seat read that from the code and did not run it.
- rm outside the working folder (rm-outside-asks, plan): for a glob or variable in a folder step, the gate judges the literal folder before it. So a glob that matches a linked folder leading outside runs unasked. The gate judges a parent step after a linked folder by its spelling, not on disk.
- rm outside the working folder (rm-outside-asks, plan): in a command the gate can split, a change of folder applies to the rest of the line. That holds even when the change fails or sits in a pipeline. So an rm after such a change can delete outside unasked. Inside a subshell or group a change of folder only adds a folder, which can only over-ask.
- rm outside the working folder (rm-outside-asks, plan): the gate judges rm only where it starts a command. Other deleting commands, such as unlink, bash rmdir, mv or a truncating redirect, are not judged by place. Recursive and forced forms keep their old reason, which names no path.
- rm outside the working folder (rm-outside-asks, plan and independent check): the gate judges heredoc lines that look like an rm. So a commit message in a heredoc with a line starting with rm and a parent step blocks headless. Builders commit with a message file, so it is rare.
- rm outside the working folder (rm-outside-asks, land review): the gate does not strip shell comments. So a plain rm inside the folder followed by a comment that names an outside path asks. Main runs it unasked. The gate refuses wrongly here; it never deletes.
- rm outside the working folder (rm-outside-asks, plan): PowerShell colon-bound parameters, pipeline input, filter and include scope and backtick escapes are not read.
- rm outside the working folder (rm-outside-asks, independent check, plan adversary, pairs): nobody probed Windows path handling, because the module uses the system's own path functions. Nobody replayed Windows command history. The seat's pairs ran on macOS only. That evidence rests on the Windows CI leg alone.
- rm outside the working folder (rm-outside-asks, final review): three home-spelling checks point home at a folder that does not exist. The gate then reads its default settings, with the journal on. Today the journal write fails harmlessly. A journal change that makes its own folder first would write under the filesystem root during that test.
- PowerShell pipe check (pwsh-lexer-oracle): PowerShell starts a comment at a hash sign glued to an operator, or to a value that starts a statement. The check reads that hash sign as part of a word. It then misses a pipe only when that comment holds a quote or a closing parenthesis.
- PowerShell pipe check (pwsh-lexer-oracle): PowerShell also starts a comment at a hash sign glued to a redirection or to a parameter's colon. The check reads it as part of the word.
- PowerShell pipe check (pwsh-lexer-oracle): PowerShell starts a comment at a hash sign glued to bare member access. The check keeps a word there. When that comment holds a quote, a piped test run, a && and a commit on the next line go unasked. Hash table and type literals have the same gap. The third build closed the gap after a second index, an array subexpression and a method call. An index that follows one of those closers still misses, as in an array subexpression's first item glued to a comment.
- PowerShell pipe check (pwsh-lexer-oracle): a here-string glued to an assignment opens only after a plain variable name with = or +=. A member, an index, a chained assignment, another operator such as -=, or uneven spacing before = still hides a later pipe. Main asks on those. The common spaced forms ask correctly.
- PowerShell pipe check (pwsh-lexer-oracle): a quoted value glued to an assignment, then a glued hash sign with an odd quote, hides a pipe main flags. A space before the hash sign asks.
- PowerShell pipe check (pwsh-lexer-oracle): in a command's arguments, a variable glued to = and a here-string opener now opens a here-string where PowerShell opens none. That can hide a later pipe. Main stays silent there too.
- PowerShell tokenizer comparison (pwsh-lexer-oracle): each class the third build added appears once in the 1,500 generated commands. The fixed cases carry the weight.
- PowerShell pipe check (pwsh-lexer-oracle): inside a string's subexpression, PowerShell stops at the first closing parenthesis. It also reads nested strings there its own way. The check keeps its outer rules there.
- PowerShell pipe check (pwsh-lexer-oracle): a few thousand nested parentheses overflow the check's stack (3,000 did on this Mac). The Claude Code hook then stays silent and writes an error note. pi's gate blocks the command instead. No honest command nests that deep.
- PowerShell tokenizer comparison (pwsh-lexer-oracle): it covers only the generated alphabet. Windows PowerShell 5.1 runs only on the Windows CI leg. One fixed case covers a lone carriage return. A machine without PowerShell, like this Mac, skips the comparison.
- PowerShell tokenizer comparison (pwsh-lexer-oracle): no check and no generated command catches five wrong versions of the pipe check. One ends every word at a closing parenthesis. One ignores a lone carriage return beside a here-string marker. One drops the low single quote. One matches typographic here-string closers only in ASCII. One treats the word after a line continuation as mid-word.
- PowerShell tokenizer comparison (pwsh-lexer-oracle): no check catches three wrong versions of its Windows PowerShell handling. One makes Windows PowerShell optional on Windows. One drops the error when Windows PowerShell is not on the path there. One drops it from the list of shells.
- Pipe check (verifier-pipe-commit-match, plan): some commands still ask although reading the status cannot change the outcome. Examples are a pipe then || true, a pipe then && echo ok, and an echo of the status. A pipe into a while loop and a loop over a pipe's output ask too. So does an echo of a piped command's output before &&. So does any earlier stop-on-error setting, even one a later command turns off, one inside a subshell that has ended, or the word errexit in any text.
- Pipe check (verifier-pipe-commit-match, plan): some status reads go unasked. A pipeline that ends an if branch before else or elif goes unasked. So does a status read after another command. A PowerShell if around a pipeline reads its output, not its status, and goes unasked. Git named through a variable or a command substitution goes unasked. So does a commit inside the pipeline, which reads its message from the pipe.
- Pipe check (verifier-pipe-commit-match, plan): Windows PowerShell 5.1 has no &&. So there the check asks only when a later command reads PowerShell's success variable, or reads the exit code after a native program ends the pipeline.
- Pipe check (verifier-pipe-commit-match, plan): asks fell by about 70 percent, not the 97 percent the scout estimated. In the plan's count, 118 commands still ask by design. Of those, 76 pipe into head and about 25 pipe an archive into tar, each before && and a commit. The owner ruled on 2026-10-21 that the pipe check stays as it is.
- Pipe check (verifier-pipe-commit-match, independent check): a 64 KB double-quoted run of escaped backticks takes about 2.8 seconds through the Claude Code hook. In-process it took up to 4.9 seconds, close to the hook's five-second limit. Main and every build take as long. Only crafted input does this, and it predates the lane.
- Pipe check (verifier-pipe-commit-match, final review): on some crafted input the check's time grows faster than the command. Repeated to 64 KB, an unclosed command substitution around a pipe takes 4.2 seconds in bash. In PowerShell it takes 8.1 seconds, past the hook's five-second limit, so the hook gives no answer. Main took 1 ms in bash there and failed in PowerShell. A brace group around a pipe takes 1.2 seconds, and a backgrounded pipe 0.7 seconds. Only crafted input does this, and no check times the scan. A stop-on-error flag of 64 KB of the letter e and then a digit takes 12.5 seconds, against 22.7 seconds on earlier builds and 3 ms on main.
- Pipe check (verifier-pipe-commit-match, final review): a stop-on-error flag written in quotes goes unasked, as in set "-e" or set -o 'errexit'. Bash honours it, and main asks. Rounds one and two missed it too. Quoting a set flag is unusual.
- Pipe check (verifier-pipe-commit-match, final review): the gate checks near the top of the pipe-guard test file run under the real home folder. That predates the lane, which added calls only inside the temp-home block.
- Pipe check (verifier-pipe-commit-match, independent check): a backslash inside git or commit, as in g\it or git co\mmit, goes unasked. Main misses those spellings too.
- Pipe check (verifier-pipe-commit-match, independent check): git, a backslash-escaped space and commit now ask. Bash runs no commit there, so the ask is extra. Main did not ask. This fails closed.
- Pipe check (verifier-pipe-commit-match, independent check): a heredoc marker quoted with a backslash can go unfound. That happens when a redirection or a pipe follows it on its line. Main misses it too.
- Pipe check (verifier-pipe-commit-match, independent check): a dollar-quoted string holding an escaped single quote is misread. A pipe, a && and a commit after it then go unasked. Main misreads it too.
- Pipe check (verifier-pipe-commit-match, wrong-code pairs): five of the seat's 74 wrong versions survive. One stops reading a backslash and a Windows line ending outside quotes as a continuation; real bash does not continue there either. One ends a pipeline at a line break after a continued line; no honest test tells it apart. One keeps main's PowerShell sample in the install check. Only the Windows install check sends that sample, and no Windows pair ran. One stops reading PowerShell's braced success variable, a spelling no row claims. One drops the backtick from the characters allowed before git. The twelfth build reads an unquoted backtick substitution as a group first, so that changes nothing tested.
- Pipe check (verifier-pipe-commit-match, independent check): nobody re-ran the independent check on the fifth to twelfth builds. The fifth made two small fixes. The sixth to twelfth fixed the three review rounds' findings, and the seventh and eighth added tests only. The seat's wrong-code pairs pin each fix.
- Pipe check (verifier-pipe-commit-match, final review): the case that stops the option search at a simple command's end pins only the semicolon. Losing the other ends would only add asks.
- Pipe check (verifier-pipe-commit-match, final review): a local assignment holding a piped substitution, then && and a commit, asks, though bash's local returns 0. Main asks too, on the safe side.
- Git Bash paths in the gate (gate-rm-gitbash-tmp, plan): pi can run another bash, such as Cygwin, standalone MSYS2 or legacy WSL. There `/tmp` is that shell's own temp folder and `/c/` is not a drive. The gate still reads Git for Windows' spellings. A hand-edited Git Bash mount table has the same effect.
- Git Bash paths in the gate (gate-rm-gitbash-tmp, plan): Git Bash fixes `/tmp` once per user while any Git Bash process runs. A Git Bash started earlier with another TMP decides it, while the gate reads pi's own TMP and TEMP. The seat read this from the runtime source and did not run it.
- Git Bash paths in the gate (gate-rm-gitbash-tmp, plan): the TMP-before-TEMP order rests on the runtime source and Microsoft's docs. CI cannot test it, because the CI step's own Git Bash fixed `/tmp` first. It is the claim most likely to be wrong.
- Git Bash paths in the gate (gate-rm-gitbash-tmp, plan adversary): after `cd /tmp`, the gate reads a relative `..` above `/tmp` under the temp folder's parent. Git Bash reads it under its install root or another drive. It usually asks. `cd /tmp && rm -f ../Temp/x` runs unasked, but Git Bash reads a path under its install root that normally does not exist.
- Git Bash paths in the gate (gate-rm-gitbash-tmp, plan): the gate reads other Git Bash root paths such as `/usr/…` on the working folder's drive. It does not read `/cygdrive/c/…`, `/mnt/c/…`, `//host/…` or `/TMP/…` at all. These usually ask, naming a path Git Bash would not delete. A root spelling that lands inside the working folder runs unasked, as on main. With neither TMP nor TEMP set, `/tmp` asks too.
- Git Bash paths in the gate (gate-rm-gitbash-tmp, plan): `rm -rf /tmp/build` and other recursive or forced forms keep their old ask. The rm-inside exemption rejects absolute targets.
- Git Bash paths in the gate (gate-rm-gitbash-tmp, wrong-code pairs): the seat's pairs ran on macOS. Only the Windows CI leg pins the gate's wiring, that it passes the platform and environment.
- Git Bash paths in the gate (gate-rm-gitbash-tmp, independent check): the gate collapses `..` before it reads any link, as it does everywhere. Git Bash follows a link first. So `rm -f /tmp/linkout/../x`, with `linkout` a link out of the temp folder, runs unasked while Git Bash deletes `x` beside the link's target. The working folder has the same gap on every system.
- rm floor (gate-rm-gitbash-tmp, plan): the floor's root check misses Git Bash drive roots. It does not count `rm -rf /c/` or `/c/Users` as a root or home ancestor. It is a non-floor ask today, so an owner allow pattern could exempt it. A gate lane fixes it.

- Git Bash paths in the gate (gate-rm-gitbash-tmp, two reviews): on Windows without Git Bash, the test header promises 16 pass and 1 skip. The real count there is 15 pass and 2 skip.
