Queue item (owner-approved 2026-10-21): "Fix the Windows test flakes. Windows failed on the first try four times in 13 hours, then passed on a re-run. One of those runs was on main, and the Windows leg blocks release."

Class: ordinary. The lane changes the install-check rehearsal (`lib/install-check.mjs` and its config), four test files, one new test file and one README sentence. It changes no nana-setup install, uninstall or doctor code, no Claude Code hook, no pi extension, no gate policy and no land or review tool. Precedent: install-check-review-launch (2026-10-20) changed the install check and ran as ordinary. `HOOK_PRODUCER_TIMEOUT_MS`, the hooks and install's steps stay untouched on purpose; changing them would make this a hook or install lane. The lane touches `packages/nana-setup/`, so the seat runs the install check locally on macOS before the land.

Ladder: one final reviewer of a different model lineage from the builder. The seat re-runs the builder's wrong-code claims.

Threat model. In scope (honest variation): hosted Windows runner load (the measured legs show process-launch stalls of 1.5 to 3.7 s beyond nominal; a cold Windows PowerShell 5.1 start can take 6 to 15+ s); an npm or registry hiccup or a Windows file lock that makes one `npm install` exit 1 fast; npm's own error lead, which npm 10 prints as `npm error code X` and npm 8 and earlier as `npm ERR! code X`; a real user's slow Windows machine. Out (deliberate forgery): a fixture or preload that fakes PASS lines, a malicious npm or pi printing a forged error-code line, anyone editing the sealed limits to hide a regression. A finding outside this model is a residual.

Harms the lane must avoid: masking a real defect. A broken pi-subagents package still fails every attempt; every failed attempt stays visible as a NOTE line; a timeout is never retried; the launch-limit bound stays below the relay's own backstop, so a relay that loses its deadline still fails R-2020 to R-2022.

## Design (smallest change)

A. Install check. Add `PI_SUBAGENTS_RETRY` to `install-check-config.mjs`. `runInstallCheck` (`install-check.mjs:290`) gains an injected `sleep = (ms) => new Promise((r) => setTimeout(r, ms))`. At `:358-359` the single pi-subagents install becomes a loop of up to `attempts`. After an attempt with no error and a numeric non-zero status, print `NOTE pi-subagents attempt ${n} of ${attempts} failed — ${npm code line ?? the existing last-stderr reason}`, where the npm code line is the first stderr line starting with a `codeLeads` entry, trimmed, from a small exported pure helper. Then `sleep(pauseMs)` before the next attempt. A timeout or launch error stops the loop at once, as today. The FAIL and PASS line formats are unchanged. `bin/install-check.mjs` needs no change (it gets the real-timer default). In `packages/nana-setup/README.md` "Install check", add one sentence: the pi-subagents install is retried up to three times, five seconds apart, after an exit failure, and each failed attempt prints a NOTE line with npm's error-code line. In `install-check.test.mjs`, `recordingRun` (`:218`, call at `:308`) gains a `sleep` passthrough defaulting to a recording no-op; the direct `runInstallCheck` call at `:637` (every spawn exits 1) gets `sleep: async () => {}`.

## Known limits (carried to HANDOFF)

- The retry can mask an intermittent real fault in the pi-subagents install that passes within three attempts. Every failed attempt still prints a NOTE line with npm's code.
- On Windows a refused pi launch returns status 1, so it is retried twice for nothing (about 10 s). Harmless.
- npm's error-code lead is a contract read from npm 10.9.7; if npm rewords it, the NOTE falls back to the last stderr line. The spawn adapter keeps the first 10,001 characters, so very long npm output could cut the code line.
- The linked-claude flake (run 39553518547) is diagnosed, not fixed. It can recur until a hook lane sizes the producer limit or the hook budget from the new R-1761 detail.
- With the larger limits, stale-copies no longer catches an install that slows from under 1 s to under 20 s, and the launch-limit test accepts a stop up to 7.5 s.
- CI re-runs cannot prove the flake rate fell (about 4 of 20 recent runs needed a Windows re-run, so three greens happen about half the time with no fix). The proof is the two meta-tests and the call-site checks.
- R-2482 and R-2483 skip on win32 by design; the forced-win32 fixtures run off Windows.
