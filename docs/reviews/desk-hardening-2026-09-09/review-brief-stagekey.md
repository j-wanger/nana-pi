## Background (what the mechanism is)

The desk (`apps/desk/server.mjs`, a loopback Node control plane) spawns `pi --mode rpc` app children and hands each one a random key in `NANA_STAGE_KEY`. The `nana-stage` extension inside the child (`packages/nana-stage/extensions/nana-stage.ts`, `lib/sign.mjs`) HMAC-SHA256-signs every "stage block" it mints and scrubs the key from its env. The server verifies on two paths: the LIVE tool event (`handleChildEvent` → `verifiedBlocks`, key + toolCallId/tool must match the event) and the LEDGER read (`GET /api/entries` → `verifiedEntries`; a `nana-block` entry that fails is REDACTED to `nana-block-rejected`, never deleted, because entries are session-tree nodes). What the signature proves: the block was minted inside an app child of this desk by the manifest's extension set. Threat model: a co-resident extension forging blocks, or a hand-edited session file. Not defended: hostile code already inside the child.

Defect being fixed: the key lived only in the desk process for that child, so a desk restart or a session resume minted a new key and every historical block was redacted (blank stage). Design rule from the punch-list: never fix it by accepting unverifiable blocks.
