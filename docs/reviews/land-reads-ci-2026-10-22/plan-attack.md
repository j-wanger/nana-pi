## M — must change the plan

### M1. D4 reads "CI applies" from main, which deadlocks a lane that removes main's workflows
- What happens: CI scope comes from captured main's tree. For a tip that deletes main's last workflow, main still tracks one, so CI applies. A `pull_request` run takes its workflow files from the PR's merge commit (inferred from GitHub's documented `pull_request` behaviour, not measured here). That merge commit has no workflow, so the tip never gets a run, and R-2587 refuses it as "no CI run" every time. The only ways out are a direct commit to main (ruling 2026-10-10 forbids it) or removing `origin` locally. The same deadlock hits a repository where Actions cannot run (disabled, billing-blocked, every run a startup failure): the lane that would remove the workflow cannot land.
- Why the draft chose main: "so a lane cannot drop its own gate by deleting the workflow". That defends against a deliberate act, which the draft's own threat model puts out of scope. The reviewed diff would show the deletion anyway.
- It also gets the reverse case wrong. A lane that adds a repository's first workflow does get a pull-request run (same merge-commit rule), but the draft skips CI for it (known limit 4).
- Change: read workflow presence from the source tip's tree. R-2590 changes in three ways. "Workflow only on the tip" moves to the CI-applies cases. A new case "main tracks a workflow, the tip deletes it" lands with the note `the tip tracks no workflow`. The README-only case reads the tip. Wrong-code pair 12 flips to "scope read from main instead of the tip": the new deletion case then refuses. Known limit 4 becomes "a lane that deletes every workflow is not held by CI; the note says so". Update the R-2592 sentences ("where the tip tracks a workflow").

### M2. GH_HOST overrides GH_REPO's host, so D6's call can go to the wrong host (measured)
- Measured, from a folder with no git: `GH_HOST=example.invalid GH_REPO=https://github.com/<owner>/<repo>.git gh api "repos/{owner}/{repo}/actions/runs?head_sha=…"` prints `error connecting to example.invalid` and exits 1. The same happens with `GH_REPO=<owner>/<repo>`. So "GH_REPO overrides any GH_REPO the seat's shell set" leaves an honest variation open: a seat whose shell sets GH_HOST, or whose gh default host is an Enterprise host. That seat gets a wrong refusal on every land.
- Measured fix: `GH_HOST=example.invalid gh api --hostname github.com "repos/<owner>/<repo>/actions/runs?head_sha=<sha>&per_page=100"` returns both runs. It does so from a git folder whose origin is `https://gitlab.com/example/fixture.git`, with GH_REPO unset. gh then needs no repository context and no placeholders.
- Change D6 to `gh api --hostname <CI_HOST> repos/<owner>/<repo>/actions/runs?head_sha=<full tip>&per_page=<CI_RUNS_PAGE_SIZE>`. Take owner and repo from M3's parser and leave the env as the process env, with no GH_REPO. This also drops a Windows-only risk: spreading `process.env` and adding `GH_REPO` can produce two keys that differ only in case. Which one wins is unmeasured (inferred risk). Reword R-2591 to "from github.com for origin's owner and repository". Its test asserts `args` equal `["api", "--hostname", CI_HOST, "repos/example/fixture/actions/runs?head_sha=<40-hex>&per_page=100"]` for each spelling, plus one case with `process.env.GH_HOST` preset that still passes `--hostname`. Pair 11 becomes "`--hostname` dropped, or owner/repo taken from the env". The POSIX fake-gh child records argv instead of GH_REPO.

### M4. The plan widens the land gate for every lane and never names what main does today that it stops
- Today an urgent fix lands minutes after its review (ruling 2026-10-11: "urgent fixes ship alone"). - Under power mode, lanes land one after another. Each lane after the first must merge main, which gives it a new tip and a new run. So consecutive lands sit at least one CI run apart, about 21 minutes (inferred from the merge-before-land rule and S1's times). The 40-land table measured each landed tip as it was, so it does not count this knock-on wait.
- Change: add these to Trade, and add two lines to "Open for the seat or the owner". First: "Gate every lane's land on the tip's whole CI run, not only setup and hook lanes on install-check? Each line gets the five decision parts: tested, numbers, trade, recommendation, why it is the owner's call. The 2026-10-11 and 2026-10-12 rulings are the owner's, so these two are the owner's call.
