**Verdict: SEND-BACK.** The core shell claims are right. The plan gets three things wrong: the exec-form rejection reasons, the scope of the "never fires" quote, and the reason for cmd.exe and `%`. It also leaves out four documented behaviours. Docs read 2026-10-12 from code.claude.com/docs/en/*.md; docs.anthropic.com/claude-code now serves the same pages.

## Claims the docs support (quotes checked word for word)
- **Hook shell.** From https://code.claude.com/docs/en/hooks#exec-form-and-shell-form: "The `command` string is passed to a shell: `sh -c` on macOS and Linux, Git Bash on Windows, or PowerShell when Git Bash isn't installed."
- **`shell` field.** From hooks#command-hook-fields: "Accepts `"bash"` or `"powershell"`. Defaults to `"bash"`, or to `"powershell"` on Windows when Git Bash isn't installed … Ignored when `args` is set." So "cmd.exe is never the hook shell" holds for current versions.
- **PowerShell tool.** From https://code.claude.com/docs/en/tools-reference#powershell-tool: "Windows with Git Bash installed: the tool is on by default for claude.ai and Console accounts" and "When the tool is enabled, Claude treats PowerShell as the primary shell. The Bash tool remains available for POSIX scripts when Git Bash is installed."
- **Tool input.** From hooks#powershell: the tool name is `PowerShell`, and "The fields match the Bash tool, with the command string in `command`". So R-1054 is grounded.
- **Matcher.** From hooks#matcher-patterns: a matcher made of "Only letters, digits, `_`, `-`, spaces, `,`, and `|`" is evaluated as an "Exact string, or list of exact strings". So `Bash|PowerShell` is exact-match, not a regex.
- **Profile output.** The hooks-guide#shell-profile-output-before-the-json quote is accurate. The docs say Git Bash *does* source the profile, which is stronger than "may": "Hooks run in non-interactive shells, but Git Bash and some configurations … still source your profile."
- **Status-line backslashes.** The statusline#windows-configuration quote is accurate. It applies to *unquoted* backslashes, and the plan already marks its use for hooks as INFERRED.
- **Decision output.** `hookSpecificOutput.permissionDecision: "ask"` is the documented PreToolUse output (hooks#pretooluse-decision-control).
- **Timeout.** `timeout` is in seconds (hooks#common-fields).
- **Placeholder rewrite.** Claude Code rewrites `${CLAUDE_PROJECT_DIR}` to `${env:…}` for PowerShell shell form (hooks#windows-powershell-tool). The plan doesn't rely on this.

## Corrections
1. **Rejected exec form, reason 2, is false.** The changelog for v2.1.139 (May 11, 2026), at https://code.claude.com/docs/en/changelog, says: "Added hook `args: string[]` field (exec form) that spawns the command directly without a shell, so path placeholders never need quoting."
2. **Rejected exec form, reason 3, is not a reason.** Exec form uses no shell, so there is no three-shell test to run. A spawn with no shell models it. The docs back the plan's exact case on Windows at hooks#exec-form-and-shell-form: "To run them in exec form, invoke the underlying script with `node` directly … The `node` plus script-path pattern works on every platform because `node.exe` is a real binary." The same section says: "Special characters such as apostrophes, `$`, and backticks pass through verbatim because there is no shell to interpret them."
   - Exec form would remove R-1052's refusal and the profile-output residual.
   - It would remove the shell-flags and PowerShell-stdin residuals.
   - It would remove `CLAUDE_CODE_SHELL_PREFIX` wrapping. Per https://code.claude.com/docs/en/env-vars: "PowerShell hooks and exec-form hooks run without the prefix."
   - Only reason 1, the entry-shape change, survives. That trade is the owner's call; the plan should not decide it on false grounds.
3. **The `"never fires there"` quote is about a different machine.** At hooks#powershell it follows the bullet "On Windows without Git Bash … Claude Code doesn't register the Bash tool at all." The owner has Git Bash, where "The Bash tool remains available". So "rarely fires on the owner's machine" is INFERRED and should say so. The `Bash|PowerShell` matcher is still right.
4. **Bash deny rules are missing from the plan.** From tools-reference#bash-deny-rules-also-turn-off-the-powershell-tool: "On Windows with Git Bash installed, denying Bash also turns the PowerShell tool off for the session. This applies to scoped rules such as `Bash(git push *)`." `CLAUDE_CODE_USE_POWERSHELL_TOOL=0` does the same. So the machine check's "raises an ask through the PowerShell tool" may legitimately arrive as `Bash`. The check should record `tool_name`, not expect PowerShell.
5. **cmd.exe and `%` have no documented basis.** The hook shell is bash or powershell, and the v2.1.47 changelog says "Fixed hooks … silently failing to execute on Windows by using Git Bash instead of cmd.exe". The `%` refusal and R-1058's cmd.exe cases rest only on cmd.exe. The one cmd.exe path in the docs is `CLAUDE_CODE_DISABLE_WINDOWS_SHELL_LAUNCHER`, which is documented for "PowerShell tool commands" only, not hooks. Either drop `%` and the cmd.exe cases, or keep them as a declared, undocumented guess.
6. **Wrong citation for double quotes.** hooks#reference-scripts-by-path says "wrap each placeholder in double quotes", which is about placeholders. The plan's literal absolute path is covered by hooks#security-best-practices: "Use absolute paths … In shell form, wrap it in double quotes."
7. **"Undocumented shell flags" is only partly true.** For PowerShell, env-vars (`CLAUDE_CODE_POWERSHELL_RESPECT_EXECUTION_POLICY`) documents `-ExecutionPolicy Bypass` "when spawning PowerShell for tool calls, hooks, and status line commands". hooks#windows-powershell-tool says it "auto-detects `pwsh.exe` … and falls back to `powershell.exe`". `-NoProfile` for hooks is not documented; "PowerShell profiles are not loaded" is listed only as a limitation of the *tool*. So the harness's `-NoProfile` is an assumption. A PowerShell profile could print ahead of the JSON just as a Git Bash profile can, and the plan does not list that residual.
8. **"doctor cannot detect this" overstates.** The docs give a way to detect it, at hooks-guide: "start Claude Code with `claude --debug` … search the debug log for `Hook output does not start with {`." From v2.1.296, hooks#debug-hooks also logs `Hooks: <event>:<match> [command] finished with status N (Xms)`, or `failed to start` or `timed out`. Doctor still can't see it, but the machine check should use both.
9. **The timeout residual is missing.** From hooks#timeouts: "A timed-out `command` … hook doesn't block the tool call … don't count on a stalled hook to act as a gate." Git Bash start-up plus node within 5 s fails open. The Windows leg should record durations. `onFailure: "block"` needs v2.1.295.
10. **The POSIX Bash-only matcher has a documented gap.** "no PowerShell event reaches it there" is true only because the matcher filters it out. The docs let macOS and Linux opt into the tool: "set `CLAUDE_CODE_USE_POWERSHELL_TOOL=1` … requires `pwsh`." A POSIX user who opts in bypasses the verifier. Declare this as a residual, since outcome 6 forbids fixing it.
11. **`CLAUDE_PROJECT_DIR` form has indirect evidence.** The docs never state its form, but their own PowerShell hook example only works with a native path: `"& \"$env:CLAUDE_PROJECT_DIR\\.claude\\hooks\\check.ps1\""`. hooks#pretooluse-input also says file paths "arrive with backslash separators, even when your hook runs under Git Bash where `$PWD` looks like `/c/project`." That points to a native form (INFERRED), so it is probably not the claim most likely to be wrong.
12. **The `"` in paths claim is documented.** It need not be marked INFERRED. https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file lists `" (double quote)` among reserved characters.
13. **Version floors are not recorded.** Git Bash hooks need ≥2.1.47. PowerShell as primary shell needs ≥2.1.126. The comma-matcher fix (2.1.191, "Bash,PowerShell") does not affect the `|` form. The plan should pin the Claude Code version it was checked against.
14. **The installer ignores `CLAUDE_CONFIG_DIR`.** This was already true and is not specific to Windows. `lib/paths.mjs:39-40` uses `os.homedir()/.claude`, while `claude/hooks/nana-shared-memory.mjs:32` honours `CLAUDE_CONFIG_DIR`. https://code.claude.com/docs/en/settings says that with `CLAUDE_CONFIG_DIR` set, "Claude Code then stores your settings … there instead." If it is set on Windows, install writes a `settings.json` that Claude Code never reads.

## Design steps that rely on undocumented behaviour, with no real-Claude-Code test on Windows
- **The PowerShell hook-shell path.** When Git Bash is absent, the plan only ever runs it under a CI emulation with guessed flags. The owner's machine has Git Bash, so real Claude Code never exercises it anywhere in the plan.
- **How Claude Code launches Git Bash.** Which `bash.exe` (`Git\bin` or `Git\usr\bin`), login or not, and its flags are undocumented. The harness's `bash.exe -c` may differ in PATH, profile sourcing and cwd.
- **Stdin through PowerShell to a native `node`.** Only the emulated harness tests this.
- **The cmd.exe cases.** They test a shell the docs say is not used, so a green result proves nothing about Claude Code.
- **R-1057's doctor check.** `spawnSync("node")` resolves from the terminal's PATH, not the hook shell's. A ✓ does not prove the hook finds the same `node`.
