**Review: land-records, final round, `86c628b9..HEAD`**

I found no MUST. The seat gets a true land history from both readers, and no record path changes a land's verdict, merge, exit code or earlier output.

**How I checked the main question**
- **The record is kept out of the land's logic.** `runLand` is now a thin wrapper around the original body, `runLandCore` (`packages/nana-pack/bin/nana-land.mjs:248`). Everything the wrapper adds is inside try/catch.
  - If `--main` is outside any repository, `common` stays null and the core's result comes back untouched. The core then runs `repoKeyOf(main)` itself, so the refusal text matches main's.
  - The core's only new inputs are `lifecycle` fields it writes, plus `mainRepoKey`. That key comes from the same `repoKeyOf(path.resolve(main))` call the core made before.
  - The record line is only ever added at the end, through `withLandRecordLine`. It adds a newline first when the earlier text lacks one, so a suite's unterminated stderr stays byte for byte.
  - Failed appends and failed reads become the one `not kept:` line or `lane line unavailable:`. They never throw into the verdict.
- **The lane line matches the build report.** nana-land renders it with `renderLandLaneLine` over the whole ledger. `build-report --lane` pairs the whole ledger, filters by lane, then calls the same renderer, so the two are equal by construction. R-2814 also pins this.
- **A refused suite's output stays out of the ledger.** The reason is the result's first line, so a suite refusal records only `suite failed (exit N)`.
- **Stages and CI state follow the plan of record.** `ci` is set to `refused` before the gh read, so a gh failure records correctly. The CI wait is computed only after `judgeRuns` passes, and only over the judged runs.
- **The build report is unchanged when the land ledger is empty.** It prints no land lines then. A land-ledger failure prints one stdout line and still exits 0.
- **No test leaks into the real clone.** The real clone's `.git/nana/` has no `land-records.jsonl`, despite several full suite runs on this lane. Every `runLand` test fixture uses `os.tmpdir()`. The install test runs nana-land with no arguments, which is an argument refusal and writes nothing.
- **Tests and pairs:** I ran `land-records`, `build-report`, `build-records` and `land.test.mjs`; all four files pass. The seat's 33 of 33 wrong-code pairs went red at `5912a41b`, and the merge after that touched no lane code.

**SHOULD**
1. **A missing final newline loses one record.** If the ledger's last line has no trailing newline, the next start glues onto it and both get skipped. The independent check found this and it is already a FEAT-008 known bug. It needs a ledger that is already torn, so it is not material.
2. **The shared module leans on build config.** `record-ledger.mjs` imports `REPORT_MILLISECONDS_PER_MINUTE` from `build-records-config.mjs`, so a module meant for both ledgers depends on one of them. It is a layering oddity only, and works today.

**NOTE**
- **Unknown outcomes read as refused.** `landViews` treats an unknown or `no end` value in a written end record as `refused`. That only matters for a forged ledger, which is out of scope.
- **The lane renderer guesses its input type.** `renderLandLaneLine` checks `recordsOrViews[0]?.start` to tell views from raw records. That holds, because raw records carry `startedAt`, never `start`, but it is fragile if a field is renamed.
- **Failed preflights are recorded too.** The start record is written before the "main is on `main`" check, so those refusals also get records. That is the plan's intent.
