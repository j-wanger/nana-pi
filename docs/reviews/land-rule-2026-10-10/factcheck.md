### risks

- Every merge from main into a lane after review now forces a new review round. Scenario: a lane is reviewed at X; another lane lands; nana-land refuses non-ff (:84). The seat merges main into the lane, and the merge commit M is uncovered, so the land is refused. M needs a new round. If the item has used its three rounds, the plan's one standard over-cap reason ("confirmation round on the final tip after fixes to named findings") does not describe a merge commit. A rebase is worse: it rewrites every reviewed SHA, so no `--reviewed` passes the ancestor check (:92).
- Under R-1004, a null verdict blocks a land. verdictWord (review-round.mjs:406-410) returns null when the output has no `VERDICT:` line, or a junk token for `**VERDICT:** LAND`. The ledger holds 156 null-verdict rounds, 10 of them since 2026-10-08. If null counts as a completed non-LAND verdict, one malformed review output blocks that revision for good. The plan does not say whether null, or an `unverified: true` SEND-BACK, counts as "completed".
- Real ledger history shows how often the new rule refuses. req-tree-b 9971070 is astra:LAND plus sol:LAND-WITH-FIXES, and req-ids 6a74cfd is astra:LAND plus sol:SEND-BACK. Under R-1004 both are refused. Every LAND-WITH-FIXES from any reviewer now forces fixes plus a confirmation round, which uses up the three-round cap faster.
- Pre-suite coverage stays valid only because two rechecks follow the suite. If coverage is computed before the suite, as :100 does today, it relies on the tip recheck (:109) and main HEAD recheck (:107). If the refusal moves after the suite or merge, "refuse before any merge" still holds, but a long suite runs for nothing. INFERRED: put the refusal next to :100, before runCommand (:102).
- The same-tree rule clashes with tracked derived files. The plan says to regenerate the requirements outline and docs/code-map.md, and the seat writes HANDOFF and session notes, all into the tree. Any of these done after the final review round is an uncovered commit and gets refused. With no exemption, any post-review fix Jake asks for at Checkpoint 2 also needs another reviewed round. The HANDOFF "Landed" line (HANDOFF.md:7) must be written before the land it records.
- The planned mutation pair cannot catch a programmatic exemption. "Re-add `--exempt` → the rejection test fails" covers the parser only. If a later change re-adds `exempt` to runLand alone (:71, :86), no CLI test fails. Tests that still pass `exempt:` would also be ignored silently, not rejected. INFERRED: runLand should reject an `exempt` key, or the tests should never pass it.
