# pwsh-lexer-oracle — plan attack (one adversary)

Verdict: AMEND

AMEND. The design is sound and the lane implements the hardening step the HANDOFF residual names, but six gaps would have shipped with it. I ran every probe in a temp folder with temp HOME against pwsh 7.4.6 and 7.6.7 (the CI images carry 7.6.5 on macOS and 7.6.6 on Ubuntu and Windows). Every plan case parses clean, both versions agree, and today's guard returns the claimed value. The `$#` flip is confirmed: `$#` is one Generic token in both versions.
1. R-1733 was narrower than its test. Its row says "open only where a token starts, never inside a bare word", but two of its cases (`'@#it's` and `<#a#>#it's`) test the other direction: no comment where PowerShell starts one. I split them out as R-1736 with a matching row, and added the `"@` twin.
2. The 9th case as written is a PowerShell parse error. `a@'` at a line end with nothing to close the quoted part gives TerminatorExpectedAtEndOfString, so pinning it pins nothing. The concrete form `Write-Output a@'\nb'; npm test | …; git commit` is parse-clean and null today. I added its `@"` twin and `a'b'<#c`, both probed red, so each of the row's four openers has a case.
3. R-1734 had no fail-open case for double quotes. `Write-Output "a”; npm test | …` closes at the typographic quote in PowerShell, which then asks; today's guard returns null.
4. The plan missed docs/requirements-tree.md. The R-291 test checks that the committed outline equals a fresh render. New FEAT-010 rows turn it red unless the build runs `node scripts/requirements-tree.mjs --write`.
5. The `$#` case must also be retitled. Its title says a comment after `$` hides the `)`, which is the opposite of its new expected value.
6. Known limit 3 understated the gap. `$a.b#c` with no index also starts a comment in PowerShell, and `Write-Output $a.b#it's\nnpm test | …; git commit` stays null after this lane (probed).
Also recorded: 14 other existing R-1062 "true" cases are PowerShell parse errors, because PowerShell cuts a string's `$( … )` at the first `)`. They stay true, which errs toward asking, so no reviewer should "fix" them.
