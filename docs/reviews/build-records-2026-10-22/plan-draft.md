# build-records: plan draft (planner, 2026-10-22)

Feature: FEAT-006 · Launch builders with execution limits (checked: pi-worker's lane mode, its lock and ceiling rows R-960 to R-963 and the precedent rows R-2578 to R-2585 live there, REQUIREMENTS.md:435-494). The new deliverable joins CAP-02's list (REQUIREMENTS.md:422), as suite-records added R-2547 to CAP-07 (REQUIREMENTS.md:1901, :1919-1920).

Class: ordinary. The lane changes pi-worker (the builder launcher), adds a pack lib, its config and one report command run through node from the checkout, moves the bench's usage-sum helpers and one pid helper into pack libs, adds the feature to the precedent check's result, and edits docs and rows. Nothing is on the install, hook or gate list. nana-setup is untouched, and the report command gets no PATH shim, as brief-check does. No hook or pi extension changes. The gate policy, nana-land, pi-review, review-round and pi-watchdog are untouched. Two stale comments in pi-review.mjs:19 and review-round.mjs:654 stay as they are for that reason (known limit). Ladder: the seat's wrong-code pairs and one final reviewer from another model family. Builder: the larger builder (pi-worker, a new lib and command, cross-folder moves, two new test files).

Stakes: medium blast, reversible. Every lane launch on every machine runs the new start and end paths. A records bug must never stop a build or change its exit code; R-2599 pins that. The records are report-only: no gate, land or review reads them, so a wrong record costs a wrong report line, not a lost build.

Threat model: honest variation in our own tools' output is in scope. That covers two or more lanes of one clone building at once and appending in the same second. It covers a pi-worker killed hard (SIGKILL, a closed terminal, Claude Code stopping a background command) and a pi that stalls, exits non-zero or writes no session. It covers a session folder holding pi-review and older pi-worker sessions, `PI_CODING_AGENT_SESSION_DIR` set to one flat folder, and a session file with a torn last line or over the read cap. It covers an unwritable ledger (`.git/nana` is a file, the ledger path is a folder, a read-only disk) and a ledger with a torn or other-schema line. It covers a brief inside or outside the worktree, a worktree removed after its build, one lane name built many times, the same lane name in two clones, and Windows drive-letter paths in pi's session-folder rule. Deliberate forgery is out: an edited ledger or session file, or a builder writing the ledger through bash, changes the report and nothing else. A reused pid that makes a killed build read as running is a residual. Public repo: this plan and every repo text name no owner and nothing about the owner's work; the measurements below name no repository but this one.

## Decisions

- **D1 · The ledger lives in the clone's git common folder: `<common>/nana/build-records.jsonl`, beside the runtime map and suite runs.** Every worktree of a clone shares it, lane cleanup keeps it, and the report runs from any checkout. User scope beside the review tally was the other choice. It would survive deleting a clone and join cross-project, but three things sink it. First, the existing lane tests set only HOME, so on Windows `os.homedir()` would read USERPROFILE and every suite run on a real machine would add fixture builds to the real ledger. Second, R-732's "pi-worker touched no ledger file" check asserts a plain run never creates `~/.pi/agent`, and a user-scope ledger invites the same write from lane runs. Third, the tally's user scope exists so one variable cannot reset a cap; nothing gates on build records. With the clone folder, a fixture's builds land in the fixture's own `.git`.
- **D2 · No lock.** Each record is one line, written with one append call. The worktree lock already orders builds within a worktree, and lines from different worktrees pair by build id, so file order does not matter. Two appends in the same instant from different lanes could in theory tear a line (inferred never on a local disk for a write under one kilobyte). The reader skips a line that does not parse and counts it in the total line. A lock would buy nothing a report needs and add a wait to every launch.
- **D3 · Two lines per build: a start line and an end line, paired by build id.** One line at the end cannot record a pi-worker killed hard, and such kills are exactly the builds the audit could not count. The start line goes after the lock is taken, before pi starts; a refused launch is not a build and writes nothing. The end line goes on every handled exit: success, failure, the ceiling, and SIGINT, SIGTERM or SIGHUP (outcome `stopped`, with the signal). A start with no end is `running` while its recorded lock file holds its pid and that process is alive; otherwise it is `killed`. The report shows one row per build either way. Build id: `crypto.randomUUID()` (chosen; unique per launch, no clock dependence).
- **D4 · The session is found by name and time, not by a pi argument.** At start, pi-worker records the folder pi will write to: the `PI_CODING_AGENT_SESSION_DIR` folder when set, else `piAgentDir()/sessions/--<encoded cwd>--/`. It uses its own `process.cwd()`, which pi inherits, so both sides encode the same string. At end, the build's sessions are the `.jsonl` files there whose name stamp is at or after the start time, whose header `cwd` is the worktree, and whose first `session_info` name starts `pi-worker-a`. The worktree lock means no other pi-worker runs there, and the name prefix drops pi-review and hand sessions. Passing `--session-id` was rejected: pi 1.0.2 warns on every new id, the warning lands in the builder's output file, and the extra argument would leave R-961's argument list incomplete. A `sessionDir` in pi settings is not followed; the cost is then unknown with the folder named (known limit).
- **D5 · Tokens and cost are pi's own numbers, summed.** The end record sums every pi-ai Usage in the matched sessions with the moved `addUsage`: assistant and tool-result messages, and usage, compaction and branch-summary entries (pi's `getSessionStats` rule). It records the summed Usage (input, output, cacheRead, cacheWrite, cacheWrite1h, reasoning, totalTokens, cost buckets), `cost` as its `cost.total`, the session file names, and the count of lines that did not parse. `calculateCost` is not called: pi already ran it on every message, and the bench takes pi's stored cost for a run's own spend (R-503). No matched session, an unreadable one, or one over `BUILD_SESSION_READ_MAX_BYTES` gives `cost: null` with a reason that names the folder. The scope asked for cost "through pi-ai's usage and cost functions"; the stored Usage is the output of those functions, and recomputing it would be a second arithmetic.
- **D6 · The record's fields.** Start: `v`, `kind: "start"`, `build`, `lane`, `brief` (worktree-relative with `/` when inside the worktree, else the real absolute path; this is the build's item), `feature` (the brief's first `Feature: FEAT-nnn`, or null), `tip` (HEAD's full id), `startedAt`, `pid`, `lock`, `laneSize`, `slot` (`builder` or `largerBuilder`), `provider`, `model`, `thinking`, `cwd`, `sessionDir`. End: `v`, `kind: "end"`, `build`, `endedAt`, `durationMs`, `attempts`, `exit`, `outcome`, `signal`, `tip` (or null with `tipError`), `usage`, `cost`, `costReason`, `sessions`, `sessionBadLines`. Names follow the review tally's (`startedAt`, `endedAt`, `attempts`, `durationMs`, `provider`, `model`); the scope's "seconds" is `durationMs`, and the report prints minutes. The review item is not recorded: lane mode refuses `--item` (R-733), and the lane name is the join key (96 of 154 match, measured).
- **D7 · Records never change a build.** Every record step runs in its own try/catch. A failed start append prints one `pi-worker: build record: not kept: <path>: <error>` line; pi still starts, and no end record or end line follows. A failed end append prints the same line form instead of the end line. The exit code and the output file are what they would be with a writable ledger.
- **D8 · Two code readers.** First, `node packages/nana-pack/bin/build-report.mjs [--repo <path>] [--lane <name>]` reads the ledger of `--repo` (default the cwd) through `repoKeyOf`. It prints one line per build in start order, one line per lane, and one total line counting builds, lanes, lanes with two or more builds, minutes, cost and unreadable lines. That total line is the audit's measure, made by code. A killed build's minutes and cost come from its sessions, using the same matcher with the window ending at the next start in that folder. Second, pi-worker's last stderr line: `pi-worker: build record: <outcome>, exit <n>, <m> min, <$cost | cost unknown: reason>; ` followed by the report's own lane line for this lane. One shared function renders the lane line for both, so they cannot disagree (the R-2543 pattern). Display: whole minutes and cents (chosen). A non-git `--repo` exits 1 with one message; an empty or missing ledger prints the total line with zeros and exits 0.
- **D9 · R-732 is retired for a narrower R-2603.** R-732 says pi-worker records nothing; a lane build now records two lines. R-2603 keeps what its three tests check: no review-round import and no review-ledger file. The tests keep their titles, and their `req:` markers move. The README Workers paragraph (packages/nana-pack/README.md:276-277) changes from "records nothing" to "records no review round", with a new Build records paragraph. pi-worker's own refusal text at :172 stays: a refused review option still records nothing.
- **D10 · Left out.** A stall outcome: telling a stall from another failure needs a field from pi-watchdog, pi-review's engine (open question 1). Back-filling the 605 earlier sessions (open question 2). Claude Code subagent builds, which never pass through pi-worker (open question 3). A Builds section in review-timeline (open question 4). Retention: none (chosen; at the measured 605 builds in 16 days and about 1 KB per build, inferred, a year is under 20 MB).
- **Builder note.** R-2603's source check runs `/admit|complete|review-ledger\.rounds/` over pi-worker.mjs with `//` lines removed. New pi-worker text must not contain those words outside `//` comments: no `completed` outcome, no `incomplete` field.

## Known limits (the seat writes them to the FEAT-006 known-bug file before the final round)

- Per clone: deleting or re-cloning a repository loses its build records, as with suite records. The report reads one repository at a time, and the same lane name in two clones is two ledgers.
- Lane mode only: a plain pi-worker run, a Claude Code subagent builder and a build done by hand keep no record. Precedent-first measured 96 of 378 recorded briefs going to Claude Code subagents.
- A stall is recorded as `failed`; the STALL line on stderr is the only sign of it.
- The cost is pi's list-price figure from its model catalog, not what a subscription bills (inferred).
- pi-worker follows `PI_CODING_AGENT_SESSION_DIR` and pi's default folder only. A `sessionDir` in pi settings leaves the cost unknown, with the folder named.
- No lock: two appends in the same instant could tear a line (inferred never on a local disk). The reader skips and counts it.
- Killed versus running rests on the recorded pid. A reused pid can show a killed build as running until the lock is removed.
- A pi-worker crash after the start record by an exception, not a signal, leaves no end record. The report then shows that build as killed.
- The review item is not recorded. Joining builds to review rounds by lane name matches 96 of 154 lane worktree folders here (measured 2026-10-22).
- Builds before this lane are not in the ledger.
- pi-review.mjs:19 and review-round.mjs:654 still say pi-worker records nothing; they mean no review round. Editing them would make this a review-tool lane.
- review-round.mjs and the knowledge build keep their own copies of the pid check.
- The ledger has no size cap and is read whole by every lane end line (inferred under 20 MB a year).
