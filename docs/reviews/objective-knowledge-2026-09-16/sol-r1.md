### A. Trust boundary — FINDING (MEDIUM)  
`packages/nana-pack/extensions/nana-objective.ts:36-41, 71-74` — Project config is correctly excluded, and `session_id` sanitization keeps knowledge dedup files under `shown/`. However, a user-configured relative `objective.path` is resolved against the process cwd, so `"path": "OBJECTIVE.md"` lets each repository supply committed system-prompt text. Home symlinks similarly delegate future content changes to their target repository, though that is documented and intentional. Smallest fix: reject relative objective paths or resolve them relative to `~/.pi/agent/`, while retaining explicit absolute paths and `~/` expansion.

### B. Fail-open discipline — FINDING (BLOCK)  
`packages/nana-knowledge/bin/nana-knowledge.ts:56-61`; `lib/hook.ts:23-35, 94-136`; `lib/tokenize.ts:22-35` — The 1500 ms budget is observational, not enforced. Reading unbounded stdin, parsing/tokenizing a huge prompt, synchronous filesystem calls, SQLite open/query under slow or locked storage, dedup reads/writes, and log appends can each block past the budget because checks happen only between operations. Missing/corrupt indexes and malformed JSON usually fail open, but `spawnBuild()` also lacks an `error` listener, so an asynchronous spawn failure can become an uncaught event and exit nonzero. Smallest fix: cap stdin/prompt size, run the synchronous hook work in a child/worker controlled by a parent hard deadline, kill it at 1500 ms, and attach a no-op/error handler to the detached builder.

### C. Detached build correctness — FINDING (HIGH)  
`packages/nana-knowledge/lib/hook.ts:23-35`; `lib/build.ts:83-88, 116-153`; `bin/nana-knowledge.ts:27-41` — Lock acquisition is a stat-then-write TOCTOU: two simultaneous prompts can both observe no lock, overwrite it, and spawn concurrent writers. Builds themselves do not acquire the lock, and any builder removes it unconditionally, so manual or stale-lock builds can overlap too. WAL reduces corruption risk, but the second writer can fail busy and readers can observe a mixed incremental generation because the build commits every 500 files. Smallest fix: acquire the lock atomically with `openSync(..., "wx")` in every build path and remove only the lock owned by that process; build a temporary database and atomically replace the completed index if readers must see one generation.

### D. Injection hygiene — FINDING (HIGH)  
`packages/nana-knowledge/lib/hook.ts:18, 76-86`; `lib/query.ts:39-47` — The final formatted block is correctly capped at 2000 characters, and newlines are flattened, but indexed markdown remains untrusted model-context text. A title or snippet such as “ignore prior instructions…” is presented without an explicit data-only boundary; “read only if relevant” does not tell the model that embedded instructions are untrusted and must not be followed. Smallest fix: frame the block as untrusted search metadata whose contents must never be treated as instructions, then retain the existing final-block cap.

### E. Objective extension semantics — FINDING (HIGH)  
`packages/nana-pack/extensions/nana-objective.ts:87-110`; `tests/objective-injection.test.mjs:75-92` — All five session reasons, read-once-per-session behavior, the 4000-character content cap, project-config exclusion, and workspace symlink refusal are implemented. The governing failure is deliberately silent, though: missing, empty, unreadable, malformed-path, or truncated-to-useless objective input produces no system-prompt marker, and the tests enshrine that behavior. This defeats the “every session must see one objective” invariant invisibly. Smallest fix: inject a conspicuous “objective unavailable” governance marker and journal/notify the cause; also clear cached state before the enabled check so live config toggles cannot expose stale prior-session content.

### F. Round cap — FINDING (HIGH)  
`app/scripts/pi-review.mjs:23-26, 52-60` — The regex recognizes only `r4`, while the real corpus extensively uses `round-4.md`, `build-round-4.md`, `astra-round-4-NO-GO.md`, and similar names; those bypass the cap entirely. Conversely, any unrelated `*-r4-*` basename is treated as a review round. `--over-cap` after `--` cannot satisfy the override, as required, although the generic `arg("--out")` parser itself searches both sides of `--`. Smallest fix: parse both bounded `rN` and `round-N` conventions from the basename, add corpus-derived tests, and restrict all wrapper-option parsing to arguments before `--`.

### G. Subtraction — FINDING (LOW)  
`packages/nana-knowledge/lib/hook.ts:69-74, 132-139`; `README.md:118-123` — `pull.log` is monitoring machinery rather than knowledge retrieval: it persistently records prompt-derived tokens, cwd, session IDs, and hits solely to support a future citation analysis. It adds synchronous work and privacy surface to every successful prompt without helping the current pull. Smallest fix: remove the log entirely; retain only the index, bounded pointer output, and dedup if repeated pointers prove noisy.

### H. Tests — FINDING (HIGH)  
`packages/nana-knowledge/tests/hook.test.mjs:79-85, 98-102`; `packages/nana-pack/tests/objective-injection.test.mjs:75-92` — The budget tests use an already-expired synthetic budget and time one healthy invocation; they do not prove termination under hung stdin, slow filesystem, locked SQLite, or spawn failure. The lock test is sequential, so it cannot expose the acquisition race, and there are no round-cap tests against actual corpus names. The most important missing test is an end-to-end hook process with a deliberately blocked operation that must exit 0, emit nothing, and terminate within 1500 ms. Implementing that test requires a real hard-timeout architecture rather than more elapsed-time assertions.

**VERDICT: BLOCK**

The hook has no enforceable wall-clock bound, concurrent builds are race-prone, and the round cap misses the repository’s dominant filename convention.
