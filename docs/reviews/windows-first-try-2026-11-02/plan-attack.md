# windows-first-try — plan attack (revision 1)

Adversary: one pass over plan.md revision 1. Probes ran on the reference Windows laptop, idle. A node child started through the shell took 99-123 ms (10 runs). `git worktree add --detach` on a one-file repository took 99-115 ms (6 runs). Lane class: `node scripts/lane-class.mjs --root . --files <the plan's six files>` prints `ordinary`. Adding `docs/known-bugs/FEAT-030.md` also prints `ordinary`.

1. **MUST: A1 leaves out the worktree-operation lock, so the 182 ms figure and R-3530's margin rest on the wrong model.** Each shard takes a lock shared across the run before `git worktree add` (`mutation-runner.mjs:556`, `withWorktreeOperationLock` at :288; the parent hands every shard one lock path at :700 and :718). The lock is polled every 25 ms (`mutation-runner-config.mjs:45`). Shard 2 may arrive at 300 ms plus its own node start while shard 1 still holds the lock. Then shard 2 waits for the release, and gap = poll wait (0-25 ms) + shard 2's own `worktree add`. That gap does not depend on the stagger at all. The CI gaps of 118 and 148 ms match this branch: `worktree add` takes about 100-115 ms on the idle laptop. The plan's branch (gap = 300 + set-up difference) is also possible, so the evidence cannot tell them apart. Either way, "the largest set-up difference measured on CI (182 ms)" was never measured. The data only says that shard 1's start-up and add ran more than about 300 ms past shard 2's start. Its upper bound is unknown, so "five times" has no base. Fix: (a) rewrite A1 with both branches. (b) State R-3530 as "the stagger exceeds shard 1's set-up span", meaning parent start to shard 1's header. (c) Add that span to the check's `why` JSON. Compute it as shard 1's header time minus the parent header time; the parent header ends in an ISO stamp (`mutation-runner.mjs:683`) and is already in `r.text`. Also add the parent-to-shard-2 span. The next failure then shows which branch failed. (d) Give the chosen stagger a provenance comment that cites this, following the pattern at `mutation-runner.test.mjs:300-310`.

2. **MUST: a 2000 ms stagger eats half the rendezvous wait. O1 points the builder at the wrong line.** The stagger check's `run()` call passes no `NANA_TEST_WAIT_MS` (`mutation-runner.test.mjs:1207`), so the probe uses its 4000 ms default (`:133`). Pair 1 starts in shard 1 and waits for pair 2's start mark (`:148-150`). That wait lasts about one stagger plus shard 2's lock wait, worktree add and baseline run. The baseline run spawns `npm config get` per key unless the npm variables are set (`mutation-runner.mjs:417-424`). At 300 ms that left about 3.7 s of slack; at 2000 ms it leaves about 2 s on a loaded runner. That trades the gap flake for a missing `GREEN 1`. O1 cites line 432, but that line is the held-shard check's own `spawn` env, not `run()`. Fix: make it a must-meet, not a builder option. The stagger check passes `NANA_TEST_WAIT_MS: String(CONTEND_WAIT_MS)` in its `run()` env. That constant (`:306`) already says "this matches the rendezvous limit", and `NANA_TEST_*` survives the runner's scrub (`mutation-runner.mjs:407`). A shard pair that never meets still fails, after 30 s.

3. **MUST: A2's likely failing side is the control's own 300 ms deadline, not a hang. A 30 s watchdog would not fix it.** The control runs `PASS_CMD` (`node -e "process.exit(0)"`, `post-edit-status.test.mjs:88`) under `timeoutMs: 300` (`:155`) through `spawn(…, { shell: true })`. On Windows that means cmd.exe plus a node start, about 100-120 ms idle here. A loaded four-job runner only needs about a 3× slowdown to pass 300 ms. Then the deadline fires (`nana-post-edit.ts:244`) and `terminate` arms the escalation timer `setTimeout(…, POST_EDIT_KILL_GRACE_MS)`, 2000 ms (`:185`, `post-edit-config.mjs:17`). The recorder then holds `[300, 2000]`, so `recorded.length === 1` fails and `controlOk` is false. A2's line "the timer counts are deterministic" is false: the count depends on load. A 5 s hang of a 100 ms child is far less likely. Fix: (a) Give the control a named deadline far above a node start, for example 60 000 ms, with a provenance comment. Assert `recorded.length === 1 && recorded[0] === CONTROL_DEADLINE_MS`; the control still proves the recorder sees an ordinary deadline. (b) Restate R-3531 to match: "the control deadline shall be far above its checker's run time, so it never fires". A longer watchdog can stay as a harmless extra. (c) Make O3's detail line carry the control's status text and the zero case's status text separately. "The last status text" is ambiguous.
