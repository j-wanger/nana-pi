# realpath-strict-fallback — must-meet

Feature: FEAT-015 · Diagnose the active environment
Class: install, hook or gate. The lane changes the pack's real-path function. nana-setup doctor, install, uninstall and the stale-copy producer compare paths through it, and so do the land and review tools (nana-land, pi-review, review-round). The gate's calls (gate-rm-inside) pass no mustExist and do not change.
Threat model: honest variation in our tools' output, platforms, volumes and configs is in scope, including a volume where Node's native path lookup fails and its JavaScript lookup works. Deliberate forgery is out.

Falsifiable sentence: when Node's native path lookup fails on a path for a reason other than a missing file and the JavaScript lookup works, realPath returns the JavaScript lookup's result instead of throwing, so doctor, the stale-copy producer and uninstall read a home that install set up there as healthy.

## Design
- One code change, in `packages/nana-pack/lib/real-path.mjs`, `realPath`'s catch. On a native error other than ENOENT/ENOTDIR, try `realpathSync(abs)` first, with or without `mustExist`. If that also throws, throw the native error under `mustExist` and return `abs` without it. The missing-file branch and `canonicalizeMissing` stay as they are.
- This restores the win-review-paths design (plan-design §1: any other native error returns `fs.realpathSync(abs)`, which keeps volumes where the native resolver fails working). That lane's SHOULD 5 asked only that `mustExist` stop returning the unresolved `abs`. Its build threw on every error other than a missing file. R-2181 pins SHOULD 5 as it was asked.
- nana-setup code does not change. Every strict compare inherits the fallback: linkOk, skillLinkState, knowledgeHookHealthy, the win32 hook-health rows, uninstall's repoReal, its preflight and per-link targets, and install's retired-hook compares. The legacy-hook root lookup in `stepRetiredArtifacts` sits outside a try.
- Prior art (looked up 2026-10-20): vite's `optimizeSafeRealPathSync` says Windows virtual and RAM disks that bypass the Volume Mount Manager (ImDisk) give EISDIR from `realpathSync.native`, and it switches to `fs.realpathSync` there.
- Spelling: the fallback returns the JavaScript lookup's spelling. That keeps the typed case, any 8.3 short name and the drive letter, and it resolves links. Both sides of a compare run on one volume, so a home installed and checked through one spelling matches. On such a volume, a second spelling of the checkout reads as another checkout again. That is a residual.
- No production seam. The pack test patches `fs.realpathSync.native` in-process and restores it in `finally`. The setup test writes a preload into its temp root at run time, as doctor-fix-line.test.mjs does, with the checkout's native real path and EISDIR written into it. The preload wraps `fs.realpathSync.native` and throws EISDIR whenever the native result lies inside the checkout. Each failing CLI run starts as `node --import <file URL of the preload>`. Node's module loader uses the JavaScript lookup, so loading still works (probed on macOS). `--import` preloads already run on the Windows leg.
- Contract notes: one sentence in the pack README's review-item paragraph. One known-limit sentence in the setup README, beside the earlier-spelling note. One row in the setup README test table. The real-path.mjs header `@errors` and doc comment.

## Known limits
- On a volume where the native lookup fails, compares use the typed spelling. There the checkout-spelling rows (R-1980 to R-1985) and the review-path rows (R-1350 to R-1356) do not hold. Two spellings are two review items. A non-LAND verdict recorded through one spelling is not seen by a land through another. nana-land refuses a case-mismatched worktree. This was main's behaviour before real-path.mjs existed, and the win-review-paths design accepted it.
- Nobody has run a RAM disk or a cloud-drive folder; the injected EISDIR stands in for one. The claim that the JavaScript lookup works there rests on vite's shipped fallback and main's earlier behaviour. It is inferred.
- Unchanged, and still on the native lookup only on such a volume: pi-worker's win32 lane paths (R-1125), the mutation runner and install-check. The adoption store key falls back to the typed path.
- A path both lookups refuse still throws under mustExist. R-2181 pins a link loop only; other codes are inferred to take the same branch.
- No row covers install's own compares under the failure. Install exits 0 under it today. A home with a legacy context-size-check.sh link makes install throw there today; R-2180 covers that lookup at the function.
- The CLI rows inject EISDIR only. R-2180 covers the other codes at the function.
- The substituted or mapped drive residual is unchanged.
