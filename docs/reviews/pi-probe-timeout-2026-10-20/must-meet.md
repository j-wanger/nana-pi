# pi-probe-timeout — must-meet

Feature: FEAT-013 · Install and connect harness runtimes (doctor rows shared with FEAT-015 · Diagnose the active environment)
Class: install, hook or gate (nana-setup install, its dry run and doctor). Ladder: final reviewer, land reviewer or seat-land.md, seat wrong-code pairs, one independent check; install-check runs locally on macOS before nana-land.
Threat model: honest variation is in scope. That covers a pi that hangs on `pi --version` or `pi install` (stuck lock or network, broken install), a shim that runs pi as a child, a slow Windows cold start, a `.cmd` pi run through cmd.exe, and the owner pressing Ctrl-C. Deliberate forgery is out. A pi that leaves its process group or job (setsid, `start`) to escape the kill is a residual.

## Feature
When pi hangs on `pi --version` or `pi install`, install, its dry run and doctor stop waiting at a named limit. They end every process that launch started and print a ✗ row naming the command and the limit, instead of hanging.

## Design
- Limits: `PI_LAUNCH_LIMITS_MS = Object.freeze({ version: 30_000, install: 120_000 })` sits in lib/steps.mjs directly above stepPiRegister (precedent: DESK_UNLOAD_TIMEOUT_MS). It stays out of install-check-config.mjs, the install check's own contract, which the install-check-turn lane edits. Provenance: chosen 2026-10-20. pi 1.0.2 on macOS answered `pi --version` and a local-folder `pi install` in 0.15 s each. pi installs local folders without downloading (pi docs/packages.md). The 120 s limit is headroom for pi's startup tidy and settings-lock retries. Worst case is 30 + 2 × 120 = 270 s for two package roots, under the install check's 300 s install bound.
- Why a relay: spawnSync's timeout kills only the direct child. Probed: a sh-wrapped fake pi's node survived. On Windows, cmd.exe dies and pi's node.exe stays. A detached spawnSync followed by a group kill works on POSIX (probed: nothing left alive). It fails on Windows because the root is gone, and Ctrl-C would no longer reach pi. So the lane adds two modules:
  - lib/bounded-spawn.mjs exports `boundedSpawnSync(command, args, options)`. Its result has the spawnSync shape (status, signal, stdout, stderr), with `error.code` ETIMEDOUT once `options.timeout` passes. It spawnSyncs `process.execPath bounded-spawn-child.mjs`, sends the spec on stdin, and passes `env: options.env ?? process.env`. Its outer timeout is the limit + RELAY_BACKSTOP_MS. It parses the last stdout line. A failed or non-JSON relay returns an error with a code and never throws.
  - lib/bounded-spawn-child.mjs spawns the command, detached on POSIX so it leads a group, and passes windowsVerbatimArguments through. It relays one JSON line, then calls process.exit, so a pi stuck in uninterruptible sleep cannot hold it. At the deadline it kills the tree: SIGKILL to `-pid` on POSIX, or taskkill with the pack's TASKKILL_ARGS on win32, falling back to the child alone. On SIGINT, SIGTERM or SIGHUP it ends the tree and exits.
  - No windowsHide on the relay or on pi, because today's launch passes none. Inferred from libuv source, not run: windowsHide with piped stdio sets CREATE_NO_WINDOW, which takes the launch off the owner's console. taskkill keeps windowsHide.
- stepPiRegister: the default spawn becomes boundedSpawnSync. A new injectable `limits` defaults to PI_LAUNCH_LIMITS_MS, and each launch passes `timeout`. On ETIMEDOUT the row is PROBLEM `pi --version gave no answer within <n> s and was stopped` or `pi install <dir> gave no answer within <n> s and was stopped`. The dry run reports the same ✗ and exits 1, as R-313 and R-1931 require.
- diagnose uses `opts.pi.spawn ?? boundedSpawnSync` and `opts.pi.limits ?? PI_LAUNCH_LIMITS_MS`. On ETIMEDOUT the detail is the same text plus ` — install: <hint>`. The row is FAIL on the real home and NOTE under --home (R-952).
- Windows still launches through winCommand and ComSpec (R-1034). A refusal (R-1035) still spawns nothing.
- Probes. The plan author ran a temp copy of bdc65eba on macOS: a 1 s limit stopped in 1.03 to 1.10 s, all 8 fake-pi processes ended, ENOENT still read skipped, and each launch cost about 30 ms more. Adversary: group SIGINT, SIGTERM and SIGHUP each ended a two-level tree when the relay had all three handlers. With the SIGHUP handler removed, SIGHUP left both processes alive.

## Known limits
- Nothing ran on Windows. The pack's post-edit kill test passes on Windows CI with the same cmd.exe → node tree, which suggests taskkill /T reaches pi's node.exe. Only the Windows CI leg proves it.
- On Windows without taskkill, or with taskkill denied, only cmd.exe ends.
- Windows Ctrl-C during a launch is untested. Whether pi gets it rests on the windowsHide inference.
- If something kills nana-setup alone rather than its group, the relay keeps pi until the limit, then ends it.
- After doctor-fix-line lands, a hung pi costs doctor two version limits (60 s): its own row, then the dry run's check.
- A kill during `pi install` can leave pi's settings lock folder, or a partly written settings.json. Inferred from pi's settings code, not run.
- Each launch starts one more node process: about 30 ms on macOS, unmeasured on Windows.
- Doctor's `node -p` and `launchctl print` probes stay unbounded. Only install is pinned for signals; doctor shares the relay.
