# Lane plan draft: suite-records (main 08c33d94; branch cut after runtime-map-live lands)

Probe: `git archive` copy of main in scratch `prep/sr2/`, `git init`, temp HOME; `probe.mjs` there. Single test files only; read-only git calls on main.

## 1. What the lane changes

Every unfiltered locked suite run keeps one record: each file's label and seconds, the exit code, wall time, job count, the tip, its merge base with main and the dirty count. Records live in the clone's git common dir, shared by every worktree, newest 300 kept. The same run reads them back. Its closing lines name the baseline, which is the newest record at or before the run's main merge base. They sort each failing file into new, failing at the baseline too, or passing in another clean run at this tip. They also list files that got much slower. After runtime-map-live, every land runs the locked suite, so every main tip gets a record. Lands make the baselines, and builders' runs read them. During a land, the lines carry runtime-map-live's land note prefix, so `nana-land` shows them (R-2530). A record problem never changes the suite's exit code.

## 3. Decisions

- **D1 Scope.** Options: `suite` (a) plus its reader, with (c) subsumed; `suite+ci` (a and b); `all` (a to e). This lane is FEAT-031, the runner's feature. CI rows sit in FEAT-019, and build and review cost belong in FEAT-035. Recommend `suite`. Default: `suite`.
- **D2 Land line (c).** Options: `subsume`, `ledger`, `file`. With `subsume`, the land's own suite record carries the land tip (from `NANA_LAND_TIP`), and main's reflog has the land time. `ledger` puts a line in the tally, which refuses every admission (measured) and breaks any older checkout's reader; the audit log rotates. `file` means nana-land writes its own land file, which no reader needs yet. Recommend `subsume`: no nana-land change, and its reader is every later run's baseline. Default: `subsume`.
- **D3 Who writes.** Options: `knob`, `always`, `parse`. With `knob`, the runner writes one record when `NANA_SUITE_RECORD_FILE` names a file. The locked suite sets it for unfiltered runs, then adds the git facts, stores, prunes and compares. `always` makes the runner write on every unfiltered run, including runs a test spawns and CI. `parse` reads the runner's printed lines. Recommend `knob`: unset means nothing changes, as R-1270 does for coverage. R-1270's text gains "per-file coverage" before "record". Default: `knob`.
- **D4 Store.** Options: `files`, `jsonl`, `map`. `files` keeps one JSON file per run in `<git common dir>/nana/suite-runs/`, newest 300. `jsonl` appends one line per run; pruning rewrites the file, and Windows is untested. `map` folds records into the runtime map, which each land overwrites, so history is lost. Recommend `files`. Default: `files`.
- **D5 Reader.** Options: `compare`, `trend`, `notice`, `report`. `compare` is the locked suite's closing lines. `trend` is a by-hand command. `notice` is a session-start line, a hook lane on the audit's hook queue. `report` is the product report confirming a FAIL, in FEAT-039. Recommend `compare` now; the per-lane slower list sums to the trend. Default: `compare`.
- **D6 Baseline.** Options: `merge-base`, `latest-land`, `previous-run`. `merge-base` takes the newest earlier record whose tip is the run's merge base with `refs/heads/main`, or an ancestor of it: one rev-list, 30 ms. `latest-land` is the runtime map's tip, which may postdate the branch. `previous-run` tells a builder only what changed since its own last run. Recommend `merge-base`. Default: `merge-base`.
- **D7 CI artifacts and the merge (b).** Options: `defer`, `upload`. With `defer`, a later ci-records lane (FEAT-019) makes each leg upload its record and compare it with the newest main run's record for its platform, using this lane's comparison code (about 2 s per step). `upload` alone makes an orphan, because CI logs already keep the same lines for 90 days. Do not merge into the runtime map: impact's readers are local builders, and per-platform seconds there have no reader. Default: `defer`.
- **D8 Build line and review cost (d, e).** Next lane, lane-costs (FEAT-035). pi-worker passes `--session-id` per attempt (pi 1.0.2, cli.md) and sums that session file's `cost.total`. pi-review's round record gains cost. Claude reviewer rounds say unknown. Readers: pi-worker's closing line, which the seat reads at every build end, and review-timeline per lane. Neither goes in the tally. Default: `next`.
- **D9 CI four at a time.** `npm test -- --jobs=4` in ci.yml (`NANA_SUITE_JOBS` is read only by the locked suite). Options: `ride`, `separate`. Recommend `separate`: a small lane that waits on nothing. Its risk is different: a Windows load flake blocks release. Its evidence is three green Windows legs on a draft PR. Inferred saving: about 20 min per CI wait (wall-time audit). Default: `separate`.

3. **R-2547** IF a locked run is filtered, `--jobs=2` included, or ends on SIGINT, SIGTERM or SIGHUP, THEN the locked suite shall set no record knob and store no record. 4. **R-2548** WHEN the locked suite stores a run record, it shall print one record line naming the newest earlier record whose tip is the run's main merge base or an ancestor of it, with that tip, its age in whole hours, whether it ran under coverage and both runs' wall seconds, or saying that no baseline exists and the next land records one. "R-2548: a locked run names its baseline record, or says none exists and that the next land records one". Records at the merge base, at its parent, and at a newer tip off main, which must be skipped. A repo with no main says none, never a git error. Red: no line.
5. **R-2549** WHEN a locked run with a baseline has failing files, the locked suite shall put each in exactly one class, checked in this order: passing in another stored record at this tip with both runs clean, failing at the baseline too, or new. "R-2549: a locked run sorts each failing file into passing in another clean run at this tip, failing at the baseline too, or new". It includes a dirty run whose file is never called flaky. Red: no lines.
6. **R-2550** WHERE a run and its baseline ran the same job count, the locked suite shall list, largest growth first and at most `SLOWER_LIST_MAX`, each file at least `SLOWER_MIN_SECONDS` slower and `SLOWER_MIN_RATIO` times slower than at the baseline. "R-2550: a locked run lists files slower than the baseline by the declared margins, largest first, and none when job counts differ". 7. **R-2551** WHILE `NANA_LAND_TIP` names the checkout's HEAD, the locked suite shall print each record line with the land note prefix. 8. **R-2552** IF the run record is missing, unreadable or cannot be stored, THEN the locked suite shall exit with the suite's own code and print one record line naming why. "R-2552: a missing, unreadable or unstorable record keeps the locked run's exit code and names why". ## 5. Class, tunables, limits, threat, files

**Class.** Ordinary. The AGENTS list names nana-land, pi-review and review-round, not the locked suite. Inferred: the seat may lift the lane to the heavier ladder, because every land runs this path. Ladder: one final reviewer from another lineage; the seat's wrong-code pairs (store a filtered run; write the record from an exit handler; take the newest record whatever its ancestry; call a dirty run flaky; compare across job counts; let a store failure exit 1; drop the land prefix); the Windows CI leg on a draft PR. Feature: FEAT-031 · Run checks reliably and without contaminating work. Carry `requirements-moved.mjs` output in both briefs.

**Tunables** (new `packages/nana-pack/lib/suite-records-config.mjs`):
- `RECORD_FILE_ENV` "NANA_SUITE_RECORD_FILE": contract (R-2545, R-2547). Chosen NANA_ name, so R-618's scrub keeps it from test files, and a runner that a test starts never writes into the real store.
- `RECORD_SCHEMA` 1: contract (R-2545, R-2546); a reader skips other schemas.
- `STORE_SUBPATH` "nana/suite-runs": contract (R-2546). Chosen to sit beside `nana/runtime-map.json` (R-1278).
- `SUITE_RECORDS_KEEP` 300: chosen. That is about nine days at the audit's rate of roughly 270 full runs in eight days (inferred), about 5 MB. Sealed by R-2546.
- `SLOWER_MIN_SECONDS` 10: chosen, above the 4.1 s largest per-file swing over three runs (runtime-map-live plan). `SLOWER_MIN_RATIO` 1.5: chosen, above coverage's 1.27 on a CPU-heavy file (that lane's attack, S3). `SLOWER_LIST_MAX` 5: chosen, to keep the land output short.
- `RECORD_LINE_PREFIX` "suite record:": contract (R-2548 to R-2552). File name `<UTC stamp>_<full tip>_<pid>.json`: chosen; it sorts by time and finds tips without parsing.
- Imported by name from runtime-map-live: `LAND_TIP_ENV`, `LAND_NOTE_PREFIX`, `MAIN_REF`.

**Known limits.** Records stay in this clone; CI and other machines keep none here. A plain `npm test` and a filtered run keep none. Seconds are parallel seconds under load. A covered land baseline makes CPU-heavy files read up to about 27% fast in a builder's plain run. Records hold no file hashes, so flaky means two clean runs at one tip. A land whose coverage run failed stores coverage labels; its plain rerun is printed as a land note, not stored. A land refused after its suite leaves a record at a tip main never reaches. Only runs built on that tip use it. A baseline older than 300 runs reads as none. A commit made during a run is not seen; the record names the starting HEAD. Paths are repo-relative, with no home path.

**Threat model.** Honest variation is in scope: two worktrees running at once, Ctrl-C or SIGTERM or SIGHUP, `--jobs=2` or `--verbose` read as filters (FEAT-031's known bug), a checkout with no main branch or no git, a detached or dirty HEAD, a lane that merged main, Windows rename and delete errors when pruning, an older schema, leftover temp files, a full disk, and a land whose coverage run failed. Deliberate forgery is out: hand-edited records, a hand-set `NANA_LAND_TIP`, and a knob pointed at another clone's store.

**Files.** `scripts/test.mjs` (the knob and the write), `scripts/test-locked.mjs` (it sets the knob and calls the store), new `packages/nana-pack/lib/suite-records.mjs` (store, baseline, sort and slower list; fs, git and clock injected, for reuse by ci-records and the report) and its config, the two tests, REQUIREMENTS.md, README.md's suite paragraph, known-bug lines in FEAT-031, HANDOFF, and the regenerated map and tree. New tests must pass under coverage too, because lands run them so.

**Build sessions.** The roster's larger builder; this is the runner every verdict passes through. Build 1: R-2545 to R-2547, R-2552 and R-1270's text. Build 2: R-2548 to R-2551, README, the CAP-07 lines, map and tree. Between them, the seat reads the store record left by build 1's own full locked run. Next lanes: ci-jobs (D9), ci-records (D7), lane-costs (D8), and report confirmation of a FAIL from records (FEAT-039).
